# Decisions

Decisions that shape the code. Newest last. Each entry says what was decided and why; reverse one by adding a new entry that supersedes it.

## D1. Rust and wgpu, shaders written once (2026-10-14)

The game is Rust on wgpu with WGSL shaders, driving Metal on macOS, DX12 on Windows and Vulkan as fallback. No per-backend shaders or code paths. No engine framework (no Bevy): our own architecture on a few libraries (wgpu, winit, an audio library, taffy, cosmic-text). Why: full control, predictable performance, one renderer everywhere.

## D2. WebGPU feature baseline (2026-10-14)

Devices are created with WebGPU's default limits and only features WebGPU also offers (plus BC texture compression when the cooker needs it). Native-only features are allowed only as optional fast paths with a fallback, and each one is agreed with Jiri first. Why: the editors will embed the same renderer through WASM and WebGPU in phase 2.

## D3. Simulation at 40 Hz on its own thread (2026-10-14)

The simulation ticks every 25 ms on its own thread; the renderer runs at the display rate and interpolates between snapshots. Why: the frozen server and lockstep input delay are built on 25 ms ticks, finer ticks keep commands responsive, gameplay is tuned at this rate, and the cost in Rust is small. The tick length is one constant. Content durations (`*Ticks` fields) are authored in fixed 25 ms units (`AUTHORED_TICK_MS`) and converted to simulation ticks on load, so a different tick rate would not change the data. Parallel work inside a tick merges results in a fixed order.

## D4. Determinism from day one (2026-10-14)

Simulation math uses deterministic functions (`libm` or fixed point), never platform math libraries; iteration orders are fixed; randomness comes only from the simulation's seeded generator. CI runs replay-hash tests on macOS and Windows, and hashes must match. Why: lockstep multiplayer and replays depend on it, and adding it later means rewriting the simulation.

## D5. Lua 5.4 through mlua for scenario scripting (2026-10-14)

Map and campaign scripts run on vendored Lua 5.4 via `mlua` with no standard libraries opened, exactly like the old sandbox: scripts reach only the `mission` API, so platform maths and Lua's own randomness are unreachable, and the unfixed string-hash seed only affects table iteration, which scripts cannot observe. Why: today's scripts target Lua 5.3 (fengari) and run on 5.4 nearly unchanged; Luau would break integer and bitwise semantics. Differences scripts can notice are listed in [simulation](simulation.md#lua).

## D6. Platform layer owns every path (2026-10-14)

No code depends on the working directory. Game data is found at `Contents/Resources/data` in the macOS bundle, `data/` beside the Windows executable, or `--data <folder>` in development; user files live in the OS user-data folder (`com.jt.canopy`). Why: packaging for any platform then needs no code changes.

## D7. Packaging and CI from M0 (2026-10-14; CI removed by D50)

CI builds, lints, tests and packages on macOS (Apple Silicon) and Windows on every push: an unsigned `.app` and an NSIS installer through `cargo-packager`. Checkouts skip Git LFS. macOS minimum version 13. Why: portability problems surface immediately; signing and installers are added later without code changes; LFS bandwidth is billed.

## D8. Apple Silicon only (2026-10-14)

macOS builds target arm64; no Intel support. The reference (weakest) machine is a base M1 with a 7-core GPU. Why: Intel integrated GPUs would set a far lower budget for little benefit.

## D9. Data mirrored, formats unchanged during phase 1 (2026-10-14)

Superseded in part by D47: the data now lives only here. `content/`, `assets/` and `art/` were mirrored from the old repository with `just sync-data` and keep their formats exactly. `canopy-content` is a strict reader of those formats. Why: the editors stay in the old repository until phase 2, so its output must work here unchanged. Identical binaries in `art/` and `assets/library/` cost nothing extra in LFS (content-addressed).

## D10. Match server and protocol frozen (2026-10-14)

Superseded in part by D48: the server now lives in `server/`; the protocol stays frozen. The TypeScript match server stays in the old repository and stays deployed. `canopy-net` implements the client side of its protocol exactly. The server embeds `content/game.json` (races, starting heroes) and action-shape validation, so new races or heroes need the server redeployed with the new content, and new action types need a server change. Why: it works, and porting it adds nothing to the game.

## D11. Profiling built in (2026-10-14)

`tracing` spans everywhere; the `profile` feature streams them and frame marks to Tracy (`just profile`). The `profiling` Cargo profile is release with full symbols. Why: performance claims come from measurements on the reference machine.

## D12. Content validation scope in phase 1 (2026-10-14)

`canopy-content` rejects anything structurally wrong (unknown fields, wrong types, unknown enum values) and enforces every cross-reference and invariant the simulation relies on, matching the old loader's rules. Pure authoring limits (for example a maximum speed of 40) are not duplicated while the old editors still validate the data; they move to Rust with the editors in phase 2. `just parity` compares the Rust reader with the TypeScript loader on the same files. Why: full constraint parity is editor work; the game needs correct reading and sound invariants.

## D13. Sampled multiplayer hash (2026-10-14)

Desync detection keeps the old design: every 8 ticks a cheap fingerprint of the id counters, jobs, stocks, outcome and a rotating sample of at most 32 actors, in the existing `hash` message. A full-state hash is not computed. Why: it is enough to catch desyncs, and hashing everything every few ticks costs too much.

## D14. Fix bugs found in the old simulation (2026-10-14)

"Behaves the same" covers intended gameplay, not defects. Clear bugs found while rebuilding are fixed and noted in the commit and, if players would notice, in the release notes. Changes to how the game plays still go to Jiri first.

## D15. Movement and pathfinding keep the old rules for now (2026-10-14)

Movement, pathfinding, collision and traffic are rebuilt with the same rules and behaviour as the old game, implemented efficiently. A proper redesign (flow fields and more) comes later as its own piece of work.

## D16. New save format (2026-10-14)

No compatibility with the old game's saves; nobody depends on them. The Rust save format is designed fresh.

## D17. Verification by play (2026-10-14)

No automated behaviour comparison against the old game. Correctness comes from scenario and determinism tests, and from Jiri playing the game once it is close.

## D18. One unsafe exception: the Lua instruction hook (2026-10-14)

`crates/sim/src/mission/hook.rs` uses about 15 lines of `unsafe` to install a raw Lua count hook that counts instructions and inspects the running function's registers for strings over 64 KiB, as the old sandbox did. mlua's safe hook cannot see registers and is several times slower per instruction. The rest of the workspace keeps `unsafe_code = "deny"`; any further exception needs a decision here.

## D19. Vision: knowledge per team, followed by comparison (2026-10-14)

Fog and remembered entities are kept once per team (allies share sight) and saved compactly (fog as runs, memories as snapshots of the entity as last seen). Sensors read the one exact `entity.position`; vision compares each sensor's position, height, radius and team with the previous pass every tick and updates only what changed, so any system that moves an entity is followed without notifying vision. Derived coverage is rebuilt on load and verified against the incremental data in tests.

## D20. Every player has a team (2026-10-14)

Teams are the only source of "ally": `canopy_sim::teams::Teams` resolves the match's slots so that every player has a team; a slot without a chosen team gets its own (the smallest number no other slot uses). Sight sharing, spells and auras that affect allies, AI and views all ask `Teams::relation` (own, ally, enemy, neutral) and never compare owners or special-case solo players. The UI need not show teams in free-for-all. Fixes the old quirk where team numbers and player indices shared one numbering.

## D21. Movement ported rule for rule, checked against the old game (2026-10-14)

Spatial model, navigation (grid A*, sectors, navmesh with the three.js 0.185 earcut ported exactly, walk-surface paths), traffic and orders follow the old code's algorithms, costs and tie-breaks (D15). During development, trajectories (positions and rotations every tick) were compared with the old game on scenarios covering crowds at chokepoints, deadlock yields, 400 units crossing a shipped map, a bridge, air units, patrol, follow and queued orders, and matched exactly; such comparisons are not kept as tests (D17). Derived data is new: compact body records in 4×4-cell buckets, per-cell blocker counts instead of owner stacks, edge and step caches, incremental mesh tiles; each is a pure function of state, so a restored match rebuilds it identically. The old envelope proof of clear sweeps is sound, so it now runs before every ground sweep, not only long ones. Units cooperate in traffic (waits-for negotiation, yielding, local claims, idle allies stepping aside) by team (D20), where the old code compared owners; route sharing and opposing-traffic search weighting stay per owner (one player's orders), and follow targets stay owned units. Game tick numbers start one lower than the old game's, which only shifts the phase of tick-hashed timing (idle strolls, separation stagger).

## D22. Combat ported rule for rule; engine ids in content are checked contracts (2026-10-14)

Targeting, swings, missiles and shells, damage, deaths, experience, camps and lookouts follow the old code's rules, numbers and tie-breaks: acquisition staggered by `tick % 8 == id % 8`, nearest by (distance, id), wind-up and recovery scaled by the attack cycle, damage summed per target and applied in id order, armour `1/(1 + k·armour)` rounded half up. During development, 25 scenarios (melee, missile and shell duels, armour, splash and slows, charges, flyers, focus fire, a 120-unit battle, assaults on buildings, camps with leash and loot, lookouts, attack, force, append, hold and attack-move orders, experience, levels, caps and fallen heroes) were run in both games and matched every tick: positions, health, swings, cooldowns, charges, slows, projectiles, corpses, loot and the random generator. As with D21 these comparisons are not kept as tests (D17).

- Damage is held in integer thousandths of a point (missile and shell damage are saved as `damageMilli`); mitigation is computed in `f64` and rounded half up as the old `Math.round`.
- Resolution asks exact sight after movement, so the world brings vision sensors up to date before step 7, and again after deaths so the dead no longer see, as the old live sensor index did.
- A dead hero stays in the entity table as **fallen** (no health, a fresh unit, on the cell it fell on) rather than being removed and re-inserted; revival (M2.5) brings the same entity back.
- **Engine-level content ids are named, documented constants checked when a world starts**, never literals in systems. The only one so far is `combat::rules::SPELL_DAMAGE = "spell"`: the damage type of untyped spell damage (mission `damage`, and later ability and item damage), which `rules.damageTypes` and `rules.damageMultipliers` must declare; content without it cannot start a match. The old `"normal"` fallback for units without a weapon was dead code (such a unit can target nothing) and is gone. New contracts go next to `SPELL_DAMAGE` and are checked in `Rules::new`.


## D23. Economy ported rule for rule; derived indexes; explicit starting workers (2026-10-14)

Jobs (deliver, construct, repair, harvest, plant with walk, wait, work, fall and return phases), the first-come harvest queue capped by `activeWorkers`, felling, depletion and regrowth, construction and its placement rules, training, rally points, pause, research, upgrades, revival, supply, wallets, accounting and defeat follow the old code's rules, numbers, messages and tie-breaks. During development, scripted matches on both shipped maps (starting gathering, mining, felling, a house and a forge built, training with a rally onto a tree, pause, research and its felling bonus, cancelled entries and sites with refunds, an upgrade refused, carriers and buildings removed with their goods and a building rebuilt, repairs, moves while carrying, defeat of three colonies and the outcome) were run in both games for up to 9,000 ticks and matched every tick: worker positions and cargo, jobs with phases and progress, wallets, accounting, building health, construction, production and research progress, the latest facts and every tree's felling state. Idle strolls and separation are tick-hashed, so these comparisons ran the old game with its tick shifted by one (D21). As with D21 and D22 they are not kept as tests (D17).

- **Derived indexes replace the old scans**: unit and building membership (followed lazily: ids are never reused, so creation shows as an advanced id counter and removal as a smaller live count), resources in 16-cell buckets, regrowing resources, and per-job aggregates (goods inbound per store, sites held by construct, repair and plant jobs) kept with the jobs and rebuilt when a save loads. `World::verify_economy` compares each with a cold rebuild. Static occupancy follows a depleted, regrown, placed, upgraded or removed blocker at once through `Spatial::sync_entity`; nothing rebuilds the whole forest.
- **Starting workers are explicit**: `spawn::placements` lists the starting units' placements, and the world gives their entities to start gathering. Nothing tests a placement-id prefix.
- **Map buildings are complete**, as in the old game, which never read `initialState.construction`; only the build command makes construction sites.
- **Supply messages name the player's own supply building**: the cheapest constructable building with `supplyProvided` in the player's race roster. The old messages said "Build a Mound" to every race.
- Every order change goes through `economy::interrupt` (via `orders::issue`), so a carrier finishes its delivery before a move, and workplaces lose their staff, as in the old game. Combat deaths release jobs, employment and paid tasks through `economy::work::release_references`; a fallen hero is revived in place.
- A decided skirmish stands still: the tick advances, nothing else runs, and commands are refused with "Match has ended".

## D24. Renderer decisions for M3 (2026-10-14)

- Every recommendation in [renderer §7](renderer.md#7-open-decisions) is accepted: one tonemapper plus a per-biome grade, MSAA 4×, one view-fitted PCF shadow map, no volumetrics or depth of field for now, the listed legacy shading paths cut, 4 blended terrain layers plus cliffs, normal-mapped rocks, authored effects converted by the cooker (their files unchanged), baked animation, live 3D portrait, presentation events from the simulation.
- **Maps up to 1024×1024**; larger maps are refused. This sets the terrain level-of-detail scheme and memory budget.
- **Interpolation delay accepted**: the picture trails the simulation by one 25 ms tick for smooth motion at any refresh rate.
- **No seasons, ever.** Biomes are the only environment configuration; a "winter forest" is simply another biome, not a season of one.
- **Lighting**: M3 matches the old game's current look inside the new, structurally clean pipeline; a separate graphics pass retunes it later.
- **Review**: each visual step comes with side-by-side captures (old game vs new renderer, same map, camera and units) for Jiri to judge.

## D25. Abilities, statuses and items ported rule for rule (2026-10-14)

Casting (targeting, eligibility, mana escrow, cooldowns, ranks, learning, autocast, cast orders and approach, prepare, channel and recover), every delivery (projectile, chain, line, charge, swarm), all sixteen operations with branches, queries, records and scales, persistent zones, toggles and auras, triggers and lifecycle reactions, summons and corpses, containment, split forms, forms, taunt, concealment and detection, spell vision, statuses (stacking, controls, damage policies, periodic effects, shields and mana shields) and items (inventory, pickup, drop and use, equipment, item auras, actives, rescue, on-hit procs, lifesteal and reflection, consumables and power-ups, regeneration accumulators) follow the old code's rules, numbers, messages and tie-breaks. During development, 49 scripted scenarios covering all of these (including a 32-unit brawl with heroes and casters autocasting, neutral camp casters, learning by level, weapon casts with autocast, death-raised summons and hero revival by ability) were run in both games and matched every tick: positions, health, mana and both regeneration accumulators, casts with phases, escrow and channels, cooldowns, ranks, autocast flags, weapon orders, statuses with timers, stacks and shields, item slots, runtimes, item statuses and bonuses, summons, containment, splits, deliveries, persistent instances, spell visions, corpses, missiles, every ability event and error, reaction queues and the random generator. As with D21–D23 these comparisons are not kept as tests (D17).

- **The ability and item libraries compile into the catalog** (`catalog.spells`, `catalog.items`) when content loads: abilities are `AbilityId` indices, statuses `StatusKey { ability, status }`, modifiers and control bits precomputed, forms resolved to definition indices. Nothing looks content up by string while a match runs.
- **Ability and item commands see the last completed tick**, like the old game, where commands ran between ticks: casts accepted with the command release on the same tick as there.
- **Ability events are presentation, not state**: about forty kinds (cast phases, impacts, statuses, summons, splits, containment, revival, combat modifiers, weapon orders), with viewers fixed when emitted; they are kept for 400 ticks (at most 1,024), drained by the client and never saved. Their presence never changes the simulation.
- **Delivery positions are integers in 1/128,000 cells**, exact for both milli-cell positions and the old game's 1/1024-cell snapping.
- **Budgets**: at most 128 lifecycle reactions (death, kill, interval, weapon release) run per tick from a queue of 512; combat reactions (hits, damage) are bounded by 2,048 queued events per tick; at most 512 deliveries and 512 persistent instances, 32 statuses per unit.
- **Spell damage that names no type uses `rules::SPELL_DAMAGE`** (D22); abilities and items add no other engine ids.
- **Old-game bugs fixed** (D14): a passive aura may carry triggers with any operations (the old content rule also scanned trigger operations, so an aura could not have a damage trigger); a line delivery needs no aim radius it never used (without one, the AI predicts a disc of the line's width at the aim).
- Revival at a building and by ability share one return: health, mana, casting state and both regeneration accumulators restart; a hero returning through an ability cannot be queued at a building, and supply counts it as returning.
- **Kept on purpose**: split members must be controllable, zero-supply non-hero units (the parent keeps its own supply and members are commanded by the player); only the first release operation is checked against the world when a cast is accepted, as later ones see the world the earlier ones changed; autocast and camp casting score only the release program, as before (the player AI that reuses it is M2.8).
- **Autocast considers only units that can matter**: those within the spell's range plus its widest area, delivery reach and the 24-cell threat radius, and the caster's own units anywhere. It skips the exact sight test for the rest, with identical choices.
- Taunted units do no work, haul nothing and enter no lookout; stunned workers neither start nor advance jobs and leave the harvest queue's waiting list, as in the old game.
- Removing an entity takes its unit body out of the spatial index at once (`Spatial::sync_entity`), as the old game did; units held by containment or a split form follow their host's whole cell.

## D26. Runtime asset pack and cooker (2026-10-14)

`canopy-cook` reads the mirrored data exactly as it is (D9) and writes one pack, `target/cooked/canopy.pack` (`canopy.pack` in the data folder of a package; `canopy_assets::find_pack` knows both). The game decodes no glTF, PNG or WAV.

- **Layout** (`canopy-assets`): a 64-byte header (magic, format version, digest of the cooked inputs), blobs, then a postcard index sorted by name. Little-endian, every blob and array 16-byte aligned. A blob is a 16-byte header, postcard metadata and plain arrays that metadata points into, so views are cast in place with `bytemuck` (no `unsafe`). `Pack::load` reads the file with one read; `Pack::open` reads the index and fetches entries on demand. Identical blobs are stored once. Entry names are the source paths (`assets/library/<id>/geometry.glb`, the path content already binds), with `#suffix` for parts (`#material0.base`, `#day`) and `@scenery` for the prototype table.
- **Models**: the authored transform (scale, pivot, forward), node hierarchy and soil offset (`groundContact: terrain` → −min y, as the old game) are folded into the vertices. Vertex: 16 bytes (unorm16 position in the model's box with the wind bend weight in w, octahedral snorm16 normal, unorm16 UV in the model's UV box); optional streams for vertex colour, leaf pivots (`_LEAF`) and skin (u8 joints, unorm8 weights summing to 255). One section per material with 16-bit section-local indices when they fit. A welded depth-only stream (positions and skin) holds every opaque shadow caster; alpha-tested sections are listed for the depth pass instead. Animated models get a joint palette in which rigidly animated nodes are joints too (felled trees, effect models), clips baked at 30 Hz as model-space 3×4 skinning matrices (Q13; frames `max(2, ⌈30·d⌉+1)` as the old bake), socket transforms per frame, the state table from `capabilities.animations` with event times normalised, and culling bounds over every frame and the wind sway. Materials are a model enum (unit, building, foliage, prop, effect) with numbers and flags.
- **Conventions are import-time inputs only**: team colour slots come from `capabilities.teamColor` (falling back to the `TC_TeamColor` name with a warning); `teamColorMask: "baseColorAlpha"` splits the base colour into opaque BC7 and a lossless R8 mask; the material extras the old renderer reads become fields, and those of cut paths (`referenceEnvironment`, `sourceShader`, `resinShimmer`…; Q5, Q6) are dropped; `foliageWind` node extras give the sway; nodes named `socket*` are sockets. The old game ignored `capabilities.wind` and the published `team_mask.png`; the cooker follows what it actually rendered and carries `capabilities.wind` alongside for the renderer.
- **Textures**: BC7, sRGB for colour roles (albedo, emissive, icons, interface, effect images, albedo tiles) and unorm otherwise, all mips, filtered in linear light: premultiplied for translucency, coverage-preserving for alpha-tested foliage, renormalised for normal maps, alpha kept independent where it is data (terrain tiles). Sizes round to whole 4×4 blocks (Catmull-Rom; the source size is kept for layout). Team masks stay uncompressed R8 (lossless). Colour grades become RGBA8 volume textures (BC volumes are not in the WebGPU baseline). No uncompressed copies are shipped: a device without `texture-compression-bc` (D2; Apple Silicon and DX12 have it) decodes BC7 at load (`Texture::decode_level`).
- **Sounds** stay 16-bit PCM: the two effect sounds are 82 KB; decoding Vorbis or Opus at load would cost more than it saves. Revisit when music arrives (M4).
- **What is cooked** is decided from the data's declarations: every glb; images of records without geometry; of model records only the images a render binding shows (the rest are copies of textures the glb embeds); not the channel images of terrain materials whose catalogue entry declares packed tiles (editor previews), but the gzip tiles themselves; other `.bin` as data; colour-grade JSON; map previews. Recipes and profiles stay in the catalogue JSON the game reads.
- **BC7 encoder: Intel's ISPC Texture Compressor through `intel_tex_2`** (prebuilt kernels for macOS arm64 and Windows x64), "fast" settings for colour and data, "basic" for normal maps. Measured on an M4 Max, 16 threads: "fast" is within 0.1–0.5 dB of "basic" on colour at about half the time; normal maps lose up to 1.5 dB with it. The pure-Rust port of the same kernels (`block_compression`, CPU path) gives the same PSNR (within 0.02 dB) and is bit-identical across platforms, but is 2–3× slower (a cold cook of 162 s against 31 s). Rejected: GPU compute encoders (results differ by GPU), `texpresso` (no BC7), bc7enc-rdo and Compressonator (C++ builds for little gain). Kept from `block_compression`: the BC7 decoder for the fallback and tests. The prebuilt kernels lack a macOS platform load command, so the cook binaries allow `linker_messages`.
- **Incremental, parallel, deterministic**: source files are hashed with BLAKE3 behind a size/mtime stamp cache; a job's hash covers the cooker and format versions, its parameters and its sources; textures are cached by image bytes and parameters, so models sharing an image encode it once; unreferenced cache files are removed. Jobs and BC7 strips run on every core; output order is fixed, maths uses `libm`, so the same inputs give a byte-identical pack. On Apple Silicon the ISPC kernel is a single NEON build; on x86 it dispatches by CPU instruction set, so Windows cooks may differ between machines (cache keys are per machine anyway).
- **Numbers** (M4 Max, shipped data, 441 MiB of cooked sources): cold cook 31 s, no-op 0.03 s, one model or icon changed 0.3–0.8 s (mostly relinking); pack 681 MiB (textures 625, models 56); loading the whole pack 89 ms (one read, warm file cache); validating every entry's metadata and views 0.4 ms.
- **Packaging** ships the pack and the JSON the simulation reads (`content/`, `assets/manifest.json`, the authoring indexes, maps) instead of `assets/library`. CI has no LFS art, so the package step cooks with `--allow-lfs-pointers` and ships a pack without it.
- **Not yet**: `Content::load` still checks that every published output exists on disk, so a packaged game cannot load content until that check consults the pack (game integration step). Pack supercompression (zstd over BC7), half-precision or sparser clip storage and the v2 effect conversion (Q11) wait for measurements and the effects step.

## D27. AI ported rule for rule from the player's knowledge (2026-10-14)

AI players (`canopy_sim::ai`) follow the old `PlayerAI` layer by layer: briefing and geography, a per-decision frame, known blockers and navigation, ability learning and casting, heroes and items, strategy, economy, reactions, operations and order continuity, with the old timings, stagger, sequence numbers (above 1,000,000), limits (four commands, one spending command and one command per actor per decision, at most 32 pending) and thresholds. During development, AI-versus-AI matches on both shipped maps were run in both games with the full content (the old game's tick shifted by one as in D21, and the fixes below switched off) and every AI command (tick, player, sequence number, action) matched: Echo Isles with two AIs through the old game's outcome at tick 34,112 (2,020 commands, 55 casts, the same winner), Turtle Rock with four AIs for 12,000 ticks (831 commands, 37 casts). Before abilities and items were merged, the same comparison with them neutralised in content matched through Echo Isles' outcome at tick 27,673 (1,503 commands). As with D21–D25 these comparisons are not kept as tests (D17).

- **The M2 finish line** (`tests/ai_match.rs`): AI-versus-AI matches end on their own on both shipped maps (with the fixes below: Echo Isles duel at tick 67,522, Turtle Rock duel at 75,786, Turtle Rock four-player at 89,025, 28 to 37 game minutes), with identical fingerprints every tick and identical final states when saved and restored half way. A 1,200-tick duel runs in CI; the full matches are ignored tests (about two minutes in release).
- **Knowledge, not views.** A decision reads what its player's view lists (own entities, others in sight through the team's fog, remembered structures, known scenery) straight from the state through `Sight`, without building or cloning a `View`; private state is read only for own entities, and enemies' mana counts as unknown.
- **Known navigation reuses the engine.** Each AI keeps reference-counted cells of known buildings and resources, and runs the engine's sweeps, clearance proofs, sector graph, grid search and navigation mesh over that known walkability. All of it is derived: rebuilt from knowledge on load, and its caches answer as a cold rebuild.
- **Placement applies the engine's foundation rules to knowledge**, not `World::can_build`, which would consult blockers and units the player has not seen. A site the simulation refuses is avoided for 1,200 ticks, as before.
- **Memory is saved state** (`State::ai`, D16): a restore checks the briefing fingerprint and that every pending AI command is in the saved queue.
- **Decisions run on this simulation's tick numbers** (one lower than the old game's, D21); the per-AI stagger is unchanged.
- **Abilities use the ability runtime's scorer** (`abilities::ai`, D25) with the old player rules: learning by newly unlocked rank, then breadth, then the race's `skillPreference`; one cast per caster per decision, the first AI binding with a useful aim; tactical intents take the first sampled destination.
- **Fixed (D14)**; players will notice the first five:
  1. The old observation boundary dropped appearance scale, so the AI saw every tree at full size: forests looked closed, units standing in them counted as obstructed, and their retreat and assembly points collapsed onto their own position.
  2. The boundary also dropped a deposit's workforce, so the recommended number of workers per deposit was never respected; it is for deposits in sight.
  3. The AI sent workers to gather remembered resources out of sight, which the simulation refuses; each refusal cost the economy pass and was retried. Gather targets must be in sight.
  4. Archer spacing compared the weapon's remaining cooldown with the match tick, so it never happened after the first seconds; ranged units now step back after a shot when a melee enemy is close.
  5. Spell scoring for the player AI follows the whole release program as it would run: every operation chooses its recipients from the units as the earlier operations left them (converted, killed, moved). The old scorer did so only for operations with a query; the others chose from the units as they were when the cast began. Enemies' statuses (public) now count in scoring; the old boundary dropped them, so the AI re-applied statuses enemies already had and ignored their immunities. Autocast and camp casting keep the old rule (D25).
  6. Sorts without a total order now break ties by id (then coordinates); an empty army composition no longer yields a NaN army target.

## D28. AI gameplay fixes kept (2026-10-15, decided while Jiri was away — review)

The five AI fixes from the M2.8 port (D27) stay: ranged units step back after a shot when melee is close, trees seen at their real scale, recommended workers per deposit respected, no gathering orders for unseen resources, spells judged by their whole program. They make the AI play as the old code intended.

From here until Jiri is back, decisions he would normally make are taken by the lead with the best available judgement and recorded here marked "review".

## D29. Audio on kira; the old effect-sound model, voice budgets and buses (2026-10-15, decided while Jiri was away — review)

`canopy-audio` ([audio](audio.md)) plays effect sound layers as the old game did and adds what the old game lacked.

- **kira 0.12 on cpal** (macOS CoreAudio, Windows WASAPI) rather than cpal with our own mixer: its audio thread does not allocate (fixed arenas, lock-free queues; our `no_alloc` test checks the renderer), it handles device loss, resampling, playback rate, tweens and tracks, can stream compressed music later, and its mock backend runs the whole mixer in CI without a device. Gain and pan are computed on the main thread with the old model, so kira's spatial tracks are unused. Without a device the game runs silent.
- **The old model exactly**: listener at the camera's ground focus, quadratic falloff from `referenceDistance` to silence at `maxDistance`, pan `lateral / max(ref, d)` with the old equal-power law (mono clips at −3 dB and the pan passed as `sin(p·π/2)` reproduce Web Audio's gains), tick-sampled timelines (offset `age × pitch`, rate `pitch × speed`, re-sync beyond 0.12 s), silence while paused. The cue lifecycle follows the old effect player: delays, durations, delivery durations, looping effects, status lifetimes, 5-second aura pulses, `follow`, cancellation, returns.
- **Voice limiting** (felt): categories Effect, World, Interface and Music with their own budgets (24, 16, 8, 2 voices); within a category the most audible requests win (the old game took the first 24), at most 6 copies of one effect sound and 4 of one world sound, a 25% hold for playing voices; world and interface one-shots of the same sound within 40/30 ms merge; inaudible and muted sounds take no voice. Losers stay virtual and keep their timeline.
- **Buses and defaults** (felt): master 1.0, effects 0.65 (the old "Spell effect volume" and default), interface 0.7, music 0.5; linear gains multiplied together as before; muted while the window is hidden (setting, on by default; the old game suspended audio in a hidden tab).
- **Presentation fixes** (D14): projectile sounds start once per cast (the old renderer could stack copies), status cues are keyed by the unit holding the status (a caster-anchored status layer no longer restarts every frame); sound layers ignore model sockets.
- **Music**: playlists with equal-power crossfades and shuffle are ready; tracks are PCM clips until music exists, when the pack format gets compressed audio and streaming (D26's "revisit when music arrives").
- `canopy-audio` depends on `canopy-sim` only for `observe(&View)`, the adapter from views to effect triggers; the effect-sound core takes plain triggers and sightings.

## D30. Biome look and presentation settings are data in `config/` (2026-10-15)

The old game defines biome lighting, atmosphere, grading, ground layers and surroundings in code (`src/content/biomes.ts`, `src/shared/environment/*`, `sky.ts`). They now live in this repository's own top-level `config/` folder, owned here and outside `content/`, `assets/` and `art/` (which `just sync-data` mirrors and would overwrite): `config/lighting.json` (day and night palettes per daylight profile, dawn and dusk phases, the ground probe and environment irradiance, shadow fitting), `config/biomes/<biome id>.json` (one per id a map may name), `config/players.json` (player colours) and `config/glow.json` (deposit glow). `canopy-render` reads and validates them strictly (unknown fields, the old editor's ranges, references to daylight profiles); `canopy-scene` resolves asset references against content; packages ship `config/` in their data folder. Values reproduce today's look: resolved numbers were checked against the old renderer (sun 3.2 from (−0.406, 0.707, −0.579) at noon in the vibrant forest, ambient 0.82, hemisphere 0.65/0.84/1.14 over 0.18) and the frames agree within a few levels of 255 (renderer §10). Derived constants are stored as data with their source: the ground probe is the old reflection cube's last mip, the environment irradiance the SH9 projection of the old procedural forest environment as it was actually sampled (upside down). Settings for effects not rendered yet (bloom, contact shadows, volumetric atmosphere) are carried so the biome files are complete. Why: biomes are content in all but location; Jiri tunes looks without code, and a later live-tuning UI writes the same files.

## D31. Renderer core for M3 (2026-10-15)

- **Crates**: `canopy-render` (device, frame graph, passes, shaders, camera maths, config types) and `canopy-scene` (the only bridge from maps and the simulation to the renderer's plain `World`). The game owns input and the window; `canopy shot` renders offscreen.
- **WebGPU baseline (D2)**: default limits; only WebGPU features, optional with fallbacks: `texture-compression-bc` (D26) and `timestamp-query` (pass timings). `indirect-first-instance` is not used (visible lists are reached through dynamic storage offsets), nor multi-draw-indirect, push constants or timestamps inside passes. MSAA attachments use the WebGPU `TRANSIENT_ATTACHMENT` usage. No exceptions are needed.
- **Today's look first (D24)**: one lighting function with a *ground* ambient model (the old terrain path) and a *standard* one (three.js physical as the old units, buildings and painted foliage used it); the one tone mapper is the old highlight shoulder, bypassed (clip) for every current biome as the old outdoor frames were; the biome grade is one baked 32³ volume. The canopy shade multiplies everything under it, as the old composite did. A retune is a separate, agreed step.
- **Shadows**: one 2048² map fitted to the view's ground slice (−6…+12 around the focus, padded, size in 4-unit steps), anchored at the world origin and snapped to texels; 8-tap rotated Vogel PCF with the biome's softness as radius (the old VSM blur radius). Casters shorter than 0.75 m are skipped, as before.
- **Terrain**: 32-cell chunks, 4 geomipmap levels chosen by projected height error ≤ 1 px, vertex-pulled heights, stitched edges; at most 4 blended layers per one-unit cell (Q7), cells aligned to the texture grid; layer lists, masks and atlas codes built once at load.
- **Scenery and buildings**: one instance buffer culled on the GPU for camera and sun every frame; one indirect draw per model section; alpha-to-coverage for alpha-tested foliage under MSAA; the old trunk sway and leaf flutter in both passes. Draw calls depend on the models present (29 on the shipped maps), not on instance counts.
- **Positions follow the old renderer**: decorative stamps stand at the cell centre `(x + 0.5, y + 0.5)`, standing trees at their resource cell, buildings at their footprint centre; scale is render asset × appearance × definition for settlement models and appearance alone for trees.

## D32. Multiplayer client `canopy-net` (2026-10-15, decided while Jiri was away — review)

`canopy-net` is the client of the old match server (D10), checked against it rather than a recording: the integration tests run `server/index.ts` from the old repository locally and play matches with Rust clients driving `canopy_sim::World`; a TypeScript client (the old repository's own `lobby.ts` and `ws.ts`) shares a lobby with a Rust one; the outbox and mailbox replay long random traces through the old `Lockstep` and `Room` and must send byte-identical messages. These tests skip themselves when the old repository, its `node_modules` or node is missing (CI). Read-only checks against the deployed server are ignored tests.

- **Wire**: client messages serialize to exactly the old client's JSON, key order included. Server messages are read leniently (unknown fields ignored), because the server spreads content records into room views (`heroes.offset`). Action key order follows `canopy_sim::Action`; the old client's call sites each had their own and nothing downstream reads it.
- **Threading**: one `canopy-net` thread runs a single-threaded tokio runtime with reqwest (lobby HTTP) and tokio-tungstenite (match socket) over rustls. The async runtime stays inside the crate: a socket task must wake both for server messages and for player commands, which a select over the socket and a channel does without polling timeouts or splitting a TLS stream across threads. The game gets synchronous handles: `Session` lives on the simulation thread and never blocks; `Commands` hands commands in from any thread, and the socket task confirms them at once, as the old client's `send` → `pulseConfirm` did. Lobby calls return `Pending` replies to poll.
- **TLS**: rustls with the `ring` provider and `rustls-platform-verifier`: the system trust store and settings on macOS and Windows, checked live against the deployed server's IP-address certificate. No certificate checks are ever disabled.
- **Server address**: the deployed `18.134.138.1` over HTTPS/WSS; `CANOPY_MATCH_SERVER`, then a game setting, override it. Plaintext `http://`/`ws://` is accepted only for loopback hosts (a local copy of the old server).
- **Beats and ticks**: server beat `T` (from 1) is the step starting at `World::tick() == T - 1` (the simulation counts one lower, D21), so its commands are queued for tick `T - 1` with their index in the slot as sequence number. The `hash` for beat `T` is `World::fingerprint()` after that step, every `checksumEvery` (8) beats, as an unsigned 32-bit number.
- **`ready` identity**: `abi` `canopy-sim-1`, `build` `canopy-<version>` (the game may pass a sharper build id) and a SHA-256 over the content the match runs on (`ContentIdentity::digest`; the game chooses the files). A Rust and an old client in one room are therefore refused with `CONTENT_MISMATCH` at the start instead of desyncing, since their simulations cannot agree.
- **Committed actions nobody can read** (or that fail `Action::problem`) are skipped by every Rust peer identically and reported; the others keep their sequence numbers.
- **Single-player** runs through the in-process mailbox with an input delay of one beat (the old `MemoryChannel`), so local and networked play feed the world the same way.
- **The end of a match**: `Session::report_outcome` sends `ended`, which ends the room for everyone. The old client never sent it, so finished rooms stayed listed as playing forever (they are visible on the deployed server). The game should send it once the outcome is decided. (review)
- **Not supported; the session stops with a reason**: the host's restart and save load (the old client handled neither; a restart also carries in-flight confirmations into the new mailbox), and joining a running match as a spectator (the server sends no history). There is no automatic reconnect, as in the old client: the server cannot replay the commits a dropped seat missed. Multiplayer has no pause (the server has none; the old client ignored pause when networked).

## D33. UI toolkit `canopy-ui` (2026-10-15, decided while Jiri was away — review)

`canopy-ui` draws the HUD and menus as [docs/ui.md](ui.md) describes; the old game's DOM HUD and stylesheets are the reference.

- **A retained tree built from data, updated immediate-style**: screens and widget templates are JSON layout documents in `config/ui/layouts/` styled by `config/ui/theme.json`, written as CSS properties (taffy parses the layout values), so the old stylesheets port almost literally. The game pushes its models into named nodes each frame; setters invalidate only what changed; layout and shaping re-run only where text sized a box. Both files hot-reload in debug builds and keep the game's values. Rejected: immediate mode (layouts would be code, taffy and shaping would rerun every frame) and a hand-written widget API (no designer iteration).
- **One quad pass**: every primitive (rounded boxes, borders, shadows, gradients, sweeps, nine-slices, images, glyphs) is a 64-byte instance of one pipeline; batches split only on image texture or scissor. The reference wgpu pass lives in the crate (feature `wgpu`); the renderer may embed it.
- **Compositing in sRGB space**, as the browser did, so the old colours, gradients and translucency match; the renderer draws the UI into a non-sRGB view of the target (or the pass linearises for sRGB targets). Textures may be bound through sRGB views (`ImageDesc::srgb_view`). (review: visible)
- **Fonts**: Outfit (the old HUD font, OFL 1.1) is bundled from the old game's npm package, converted from WOFF2. Georgia and the system UI font, which the old game took from the operating system, are again taken from the operating system (both ship with macOS and Windows; neither may be redistributed), with Outfit as the fallback. Recommended follow-up: bundle Gelasio (OFL, metric-compatible with Georgia), which needs a font download that was not made unattended. (review: visible)
- **Tooltips show at once** (`delay-ms: 0`), as in the old game; the delay and the warm switching window are theme values. (review: felt)
- Boxes default to `position: relative` (absolute children are placed in their parent, as every old HUD rule assumed).
- Requested font weights snap to a static family's faces as CSS matching does; cosmic-text alone matches exact weights only.
- Tests use their own theme and layouts; text tests fall back to system fonts when the bundled font is a Git LFS pointer (CI). The gallery render test skips without a GPU adapter.
- `Ui` is not `Send` (taffy styles hold calc pointers): it lives on the window thread.

## D34. Water, post effects, surroundings and render scale for M3 (2026-10-15, decided while Jiri was away — review)

[Renderer §4.6 and §9](renderer.md) describe the result; [captures](captures/README.md) compare it with the old game.

- **Water is redesigned around the old shading model, without a scene copy.** The old water copied the frame's colour and depth, marched 64-tap screen-space reflections and refracted the bed. Here it is drawn inside the MSAA forward pass in two draws over the same fragments: one multiplies the bed by the hue of the water column's absorption, the other blends the surface with premultiplied alpha carrying the rest of the bed's dimming. Together they reproduce the old per-channel transmittance exactly (echo-isles shallows within 1–2 of 255). Every other old term is kept (body colour, caustics, swell bands, the old woodland reflection cube, glints, shore/crest/flow foam, cloud and canopy shade, unit wakes). Dropped on purpose: refraction (about 2 px at RTS zoom) and screen-space reflections (2–4 % of the colour at the 56° pitch). Dual-source blending would make it one draw but WebGPU allows it only with a single colour target, and the forward pass has two (below). (review: the look)
- **Ripples are ported one-to-one** (1.7 m spacing, 3 per body and 256 per frame, 1,536 rings, 2.8 s, 768² RGBA16F over 160 m, Gaussian crest). The live world feeds `Renderer::ripples_mut().update(movers, field, seconds, focus)` every frame with plain `Mover`s (id, position, walking surface, elevation); bridge decks come through the `WaterField::walk` surface id.
- **Linear depth is a second forward colour target** (RG16F: the view depth rounded to 11 significant bits plus the remainder, exact through the MSAA resolve for interior pixels; WebGPU resolves neither depth nor R32F). It costs no memory traffic beyond one resolved RG16F image, where storing the multisampled depth would cost about 66 MB per 1080p frame. **Contract for every forward pipeline** (units and effects included): declare `targets::forward_targets(blend, writes_depth)` and return `scene_out(colour, world)` from opaque fragment shaders (`frame.wgsl`); transparent ones pass `false`. The water writes its surface, so post effects stop at the water like the old ones.
- **Post effects run only where the biome uses them and the quality allows**: the frame graph is rebuilt from `FrameFeatures` (water, contact, bloom, haze) when the world, biome or settings change; a pass that does not run does not exist. Contact shading, bloom and the volumetric haze follow the old `BeautyPass` and `AtmospherePass` with their budgets (effect buffers at most ½ scene and ~180k pixels; haze low/medium/high = 0.33/0.5/0.66 scale, 16/24/40 steps, 180k/360k/900k pixels; medium by default as in the old game). The old composite clipped every surface at the plane `waterLevel − 0.03` and committed-cell maps leave `waterLevel` at 0, so the old game had no contact shading on ground below y ≈ 0.05; that quirk is not kept (D14) — ground around the shipped maps' shores now gets contact shade. (review)
- **Render scale** is a quality setting (0.5–1; the scene renders with MSAA at the scaled size and the final pass upsamples with a light unsharp mask, strength 0.25). Default 1. **Recommendation for the base M1**: 1.0 at 1080p, 0.75 on Retina panels (2560×1600 → 1920×1200 internal), from the measurements in renderer §9 scaled by the GPUs' throughput. (review)
- **Surroundings** follow the old generator exactly (seeded LCG, anchor rings, forks, leaf grid) so the same biome and map size place the same forest; the data moved to `config/biomes/*.json` `surroundings.forest` (scenery ids, rings, leaf colours, bark texture) and the shared water textures to `config/water.json`. As before, the camera's map fit keeps the forest out of every play and spectator view; it shows only in free views.
- **Pass timings on Apple GPUs are coarse**: timestamps at pass boundaries attribute work to neighbouring passes (the final pass always reads 0 ms). `canopy shot` therefore also prints the median submit-to-idle time of the measured frames; budgets use both.
- **WebGPU baseline (D2)**: nothing new is requested; no exception needed.

## D35. The live world: simulation thread, presentation, interpolation and live models (2026-10-15, decided while Jiri was away — review)

M3.3 makes matches watchable: `just play --spectate <map> [--players N]` runs computer players on the map's starts; `canopy shot --tick N` simulates to a tick first (renderer §9, §10).

- **Simulation thread** (`game/src/sim.rs`): the world steps on its own thread through `canopy_net::Session::local` (observer seat), so multiplayer later uses the same path. Tick `n` belongs to simulation time `epoch + 25 ms · n`; the thread computes it **one tick early** so a tick's cost (up to 25 ms) never shows as a hitch, and never earlier, so the match never runs faster than real time. Behind by more than 8 ticks, it catches up at full speed for those 8 and moves the schedule for the rest (the match slows down instead of skipping or bursting; results never depend on timing). A player's commands will therefore reach the screen one tick (25 ms) later than with no lead. (review: felt)
- **Hand-off**: the newest 4 presented ticks sit in a ring behind a mutex the simulation holds only to push a pointer; the render thread checks an atomic tick counter and `try_lock`s, keeping what it has when the lock is busy. It never waits for the simulation.
- **Presentation runs on the simulation thread, once per tick** (`canopy_scene::live`): the observer view becomes posed models (transform, owner colour, opacity, up to three clip poses) with the old game's rules; animation state choice and clip clocks advance per tick (D24's tick-addressable animation), so the same tick presents identically (shots are deterministic) and the render thread only interpolates. It costs about 0.2 ms a tick in a duel and 1.3 ms with 500 fighting units (M4 Max).
- **Interpolation** (Q15): the picture shows simulation time minus one tick, between the two presentations around it: positions and scales linearly, rotations along the short arc, poses clip by clip (looping clips wrap, restarted one-shots take the new time). New models, model changes and moves over 3 cells in a tick do not blend. No extrapolation: a late tick holds the newest picture.
- **Animation as in the old game** (`animation.rs`): clips play at 1.5×; aliases sharing a clip (run, charge) keep their phase; one-shots return to idle (not death); linear cross-fades from the current weight, at most the current and two fading clips; attack wind-up maps onto `[0, contact]` and recovery onto `[contact, 1]` from the swing's ticks; work strokes follow the authoritative cycle and face the work; cast phases follow the old `castAnimation`; a hit plays the hit reaction when standing and tilts the body for 0.22 s. The engine's state names (`idle`, `walk`, `run`, `charge`, `attack`, `hit`, `cast`, `death`, `carry*`, and the content's work animations) and the cargo node `socket_back` are the old renderer's contract with the asset pipeline, not content ids.
- **Static and live split**: map stamps and every tree stay in the static scene (D31); a tree leaves it (a 16-byte flag write) once struck or gone and the live scene plays its hit, fall and decay clips at 1× from the felling ticks. Everything else is live: units, buildings (depletion stages, construction scaffolds rising until the race's reveal point, model swaps on upgrade), items on the ground, carried goods at the back socket, corpses, missiles and shells.
- **Live models on the GPU** (`canopy_render::actors`): CPU culling against the camera and the sun (cheaper than a compute pass at these counts, and it keeps the draw list), instances sorted by model with camera-visible ones first, one skinning job each; a compute pass blends model-space 3×4 matrices (Q13) for up to three poses between two baked frames into per-instance palettes; one instanced draw per model section reads a contiguous range (direct draws with a first instance, which the WebGPU baseline allows). Rigid models skin with one identity joint, so one pipeline serves everything. Statics and live models share one material module (`shaders/lib/material.wgsl`, `material.rs`). No WebGPU exceptions.
- **Deaths follow the old renderer**: a unit that dies in sight plays its death clip for two seconds where it fell (a flyer drops to its floor at `15 t²`), then vanishes; fallen heroes are hidden until revived. The simulation's raisable corpses are not drawn, as before.
- **The view lacks one fact**: whether a unit is held inside another entity (`contained`, `release`). The presenter reads it from the world on the simulation thread (observer only, so nothing leaks); the view should carry it (follow-up for `canopy-sim`).
- **Projectiles** use the shooter's weapon effect layers (model, size, rotation, offset, arc) from content; the layer colour tint is not applied (every shipped weapon layer is white).
- **Shot and stress tools**: `--tick N` (deterministic, presents every tick), `--camera battle[,zoom]` (centre of the densest group of swinging units), `--crowd N` (eight players with N animated soldiers each around the middle of the starts, each with a small building so skirmish rules keep them in), `--colors i,j,…` (player colour per slot, for colour reviews).
- **Dev builds optimise `canopy-sim` and `canopy-scene`** (opt-level 2, like the cooker): unoptimised, a mid-game tick costs over 25 ms and `just play --spectate` could not keep time.
- **Measured** (M4 Max, 1080p, after the water and post effects; base M1 still to measure): the 8 × 50 crowd view (491 animated units visible, 554 shadow casters, 26,700 joints) takes 3.2 ms from submit to idle against 2.0 ms for the same view without the crowd, 0.4 ms of CPU to record and 0.013 ms to interpolate; the palette pass costs 0.01 ms. In a window (Retina, about 3200×1800) a 450-unit battle ran at 245 fps uncapped before the post effects. Scaled to the base M1 (about 7× less GPU), 400+ units in view would cost about 8 ms on their own at 1080p, so the worst case needs a cheaper unit path (fewer shadow casters, lower-detail shadow meshes or level of detail) or render scale below 1 to stay under 16.7 ms; ordinary fights of 50–150 units fit. (review: performance against quality) The simulation thread: 0.3–0.6 ms a tick in a duel, 8–16 ms with 400 fighting units (spikes to 30–50 ms as the armies meet, which the one-tick lead hides up to 25 ms), the simulation's own cost (M2).

## D37. Simulation performance work keeps results bit-identical (2026-10-15)

Speed-ups in `canopy-sim` must not change a single simulated value: every tick fingerprint and the final saved state stay identical, checked with the digest of `just bench-sim` (crowd battles and AI matches) before and after, besides the determinism tests. Concretely: caches are pure functions of the state they read and are forgotten whenever that state can change (autocast remembers sight answers and unit snapshots only until the next cast); "is there any" queries may test candidates in any order and skip ones that provably cannot answer (the sight index skips sensors not shared with the asking team; attack approach first tries the bodies touching the actor); "the first in order" searches keep their order (attack approach pops a heap and sorts only the candidates that pass the pure tests). A faster rule that would change tie-breaks or outcomes is a gameplay change and goes to Jiri (D14).

- The measured crowd battle (`canopy shot --crowd N`) lives in `canopy_sim::crowd`, so the shot tool and the benchmark run the same scenario. `World::step` marks its steps with `tick: …` spans for Tracy and the benchmark.
- Numbers and the remaining hot spots are in [simulation § Performance](simulation.md#performance).

## D42. Render performance: benchmark, levels of detail, graphics presets (2026-10-15, decided while Jiri was away — review)

- **One benchmark** (`just bench-render`, `crates/render/src/bench.rs`, `game/src/bench.rs`): fixed scenes (player base, zoomed-out spectator, the 8 × 50 crowd battle with 256 effect cues, deep water, the deep-forest look, the menu, the HUD) at 1920×1080 and 2560×1600, measured as wall time from recording to idle and every pass alone in its own submit, minus the fixed submit cost; the fastest fifth of 60 frames. Apple's pass timestamps attribute work to neighbouring passes, so they are not used for decisions. The frame log and the debug overlay show a sampled submit-to-idle time instead of summed timestamps (the old "18 ms at 120 fps" reading was that artefact).
- **Levels of detail for live models**, cooked: meshoptimizer simplifies each model (from 1,024 triangles up) into index lists over the same vertices, each level the smallest within a share of the model's size, topology kept (no piece vanishes, seams stay closed). At run time a model draws the coarsest level whose deviation is under `lod_pixels` on screen (High 0.5 px; nobody should see a switch). Shadow casters use the same levels.
- **Cheaper shadows**: one rotation per pixel of a fixed Vogel disk (one sine and cosine instead of one per tap); surfaces facing away from the sun skip the taps; materials skip maps they lack.
- **Graphics presets**, chosen on first run from the adapter's name and changeable in Settings → Graphics (each option can still be set alone): *High* is today's look; *Ultra* finer levels of detail and high haze; *Medium* at most 1440 × 810 scene pixels (upscaled with the sharpen), no contact shading, low haze, LOD 1.5 px, 1024² shadow map; *Low* 1152 × 648, no bloom or haze, LOD 3 px. Apple Pro/Max/Ultra and discrete GPUs get High; **base Apple chips (M1–M4) get Medium**; other integrated GPUs Low. (review: visible — Medium on a base M1 renders below native resolution)
- **Measured** (M4 Max, 40-core GPU): High, worst scene (spectator at 2560×1600) 4.8 ms a frame, the crowd battle 4.1 ms; Medium, worst 2.7 ms (spectator), crowd 2.2 ms, a player view 1.5 ms. CPU recording stays under 0.5 ms, the HUD 0.02 ms. Scaled by GPU throughput (a base M1 has about a seventh), Medium's worst view is about 15–16 ms and a player view about 9–10 ms: 60 fps on a base M1, with the zoomed-out spectator view the tight case. The spectator view is vertex-bound (about 1 million forward and 1 million shadow triangles, mostly scenery and terrain, which Low barely reduces); if the real M1 misses 60 there, the next steps are scenery levels of detail and a shadow distance limit. **Not measured on a base M1** — measure with `just bench-render --preset medium` and adjust `Preset::for_adapter`.

## D44. Building placement as Warcraft III, and drawn foundations (2026-10-15, agreed with Jiri — visible parts review)

"Choose flatter ground" refused building almost everywhere: the foundation rule (at most 2 m of relief across a footprint, at most 40 cm between neighbouring cells) is the old game's, but the shipped maps are imported Warcraft III maps with natural rolling ground, where footprints of 20 cells span 2–9 m. On dry ground only 3.9 % (Echo Isles) and 16.4 % (Turtle Rock) of lattice positions took a 20 × 20 hall, 19 % / 33 % a 12 × 12 barracks, 39 % / 49 % an 8 × 8 house. Warcraft III does not check height at all: buildability is a per-cell pathing flag (cliff edges, ramps and water unbuildable), the building stands at its centre's ground height, and deep model bases and a ground texture hide the uneven ground.

- **Placement** (`terrain::footprint::foundation_fits`, used by construction validation, start validation, the AI's placement search and the client's ghost): no limit on relief across a footprint; a cell is too steep when the ground rises more than **80 cm into a 4-neighbour inside the footprint** (`MAX_FOUNDATION_STEP_CM`). That blocks cliff faces (2–5 m steps) and ramps (about 1 m per cell, unbuildable in Warcraft III so chokes cannot be walled) and only 0.3 % (Echo Isles) / 1.0 % (Turtle Rock) of ordinary cell steps. Steps across the footprint's border are not checked (as before): a footprint may stand next to a cliff edge, only not across it. The message stays "Choose flatter ground"; water, the doorway and every other check are unchanged; integer centimetres as before (D4). Measured on all dry lattice positions: halls 92.0 % / 84.6 %, barracks 94.5 % / 90.2 %, houses 95.7 % / 92.8 %. The steepest accepted hall sites have 13–15 m of relief (median 5.1 m on Echo Isles, 3.6 m on Turtle Rock). AI duels on both maps still end in a win (Echo Isles 19.6 game minutes, Turtle Rock 28.2; before: 28.1 and 31.6), with 13–26 buildings placed per side.
- **Foundations** (render only, `canopy-render` `terrain/foundations.rs`, renderer §9; review: visible). Buildings still stand at their centre's ground height. Under every building (construction sites and resource deposits included) the ground itself rises to meet the base where it falls away, as if the terrain were sculpted there. Jiri rejected two earlier versions: a dirt patch and dirt banks ("could the foundation take on the texture below it?"), then cliff-walled terraces ("Minecraft"); this is the third.
  - *Shape*: a flat pad over the footprint (corners rounded with 40 % of the shorter half side, at most 3 units) 5 cm under the base, and a mound around it: smoothstep-profiled from the rim (a soft shoulder, lit as the pad there) to a toe that eases tangentially into the ground (2 cm under it), 2.4 × the drop at the rim wide (about 32° at its steepest), at least 0.4 and at most 5 units (steeper only beyond about 2 m of drop), the width varied along the rim by a low-frequency wave (±30 %) so the outline is organic. Ground heights are pulled from the terrain's height texture in the vertex shader with the terrain's own triangle interpolation, so where the ground is level with or above the base nothing changes.
  - *Look*: the terrain's own surface at the same place: `ground_at` in `terrain.wgsl` (the cell's layers and painted coverage, the same world-space mapping and the terrain's own cliff rule, lighting, shadows and fog). No cliff or other material is added. The mound is lit with its own smooth normal, which turns into the terrain's normal towards the toe so lighting is continuous across the seam; no ambient darkening is added. Measuring texture distance along the mound's surface to avoid stretching on steep faces was tried and dropped (it smeared the painted coverage); faces steeper than about 40° show some stretching of the ground texture.
  - *World UI*: ground marks (selection rings, rally routes, the placement grid) drape over the mounds: the scene's walking heights include each mound's surface, computed on the CPU by the same formula (`Foundation::surface`).
  - One instanced draw and one shadow draw for all footprints in view (4,080 vertices each: 80 spokes × 8 bands and the pad's fan; CPU-culled per frame); the list is compared each frame and nothing else is redone. The foundation follows what the viewer sees and remembers (the presentation's bodies), so it never reveals an unseen building.
- **Cost**: no measurable change (M4 Max, frame to idle, three alternating runs; best frames within 0.1 ms): a player base at zoom 1 (11 foundations), the steep test sites (10), a spectator view at zoom 3 (48).
- **For review**: mounds spread up to 5 units beyond a footprint on big drops, where units walking beside the building stand on the true (lower) ground and are partly hidden; on the steepest accepted sites the ground texture stretches on the mound's steepest part.

## D45. Trees are picked by their drawn shape and ringed on hover (2026-10-15, decided while Jiri was away — review)

Jiri reported that right-clicking a tree needed a precise click on the cell of its root. The old game raycast the instanced forest's meshes (`renderer.pickGameEntity` → `props.pick`) but its hover pick skipped scenery, and it never drew a ring on trees.

- **A tree's pick shape is a lathe of its model** (`picking::TreeProfile`): eight equal height bands from the soil to the top, each an upright cylinder as wide as the model's widest rest-pose vertex in that band (× 0.85, as leaf and needle cards are mostly transparent at their tips), at least 0.45 m (the trunk). It follows a pine's cone or a broadleaf's ball on a trunk, is tested exactly against the camera ray and costs a few dozen operations per tree near the ray. Built once per match from the static scene's tree instances (`tree_slots`) and the pack, one profile per model. Trees are bucketed on an 8 m grid; a ray tests only the buckets under the stretch of it between the forest's highest top and lowest root. Forgiving volumes rather than triangles, so the gaps between branches pick too. (review: felt)
- **What picks**: units' screen-space capsules first, as before (a unit in front of, or under, a tree wins). Then the building, item or resource whose footprint holds the ground point and the nearest standing tree the ray enters before the ground (0.5 m slack for the trunk's foot): whichever the ray meets first, a building by its body cylinder. Known scenery without a drawn shape keeps the old footprint rule. Hover uses the same pick.
- **Standing** means known to the player, something left to harvest and not falling: a struck tree stands and is harvested until it falls, as the old proxies were pickable while `hp > 0`; a falling or felled one is not pickable.
- **The tree ring is new** (the old game had none): when the selection holds a unit that could gather the hovered tree (the right-click would order a gather), the world UI draws the neutral hover ring of a mine — yellow, faint — around the tree, just outside its crown's widest reach (+0.25 m), because a ring at the trunk hides under the branches from the overhead camera. Nothing shows with nothing selected, with buildings or non-harvesters, or in a command mode. (review: visible)
- **No gather cursor**: the game has only system cursors (the old canvas had none for gathering either).

## D46. Damage effects: burning buildings and hit dust (2026-10-15, Jiri asked for them — review: visible)

New, not in the old game. Both are presentation only: the presenter reads the view's health and swings, the simulation is untouched, and every random choice is a hash of entity ids and ticks. [Captures](captures/damage-fx/).

- **Damaged buildings burn** (`canopy-scene` `damage.rs`): a built building in sight (not a construction site, not a remembered one under fog, not a deposit or mine) burns below 90 % of its health. Its severity rises linearly to 1 at 15 %. It has 2–6 fire spots by size (one per 2.4 m of its larger side). They ignite one by one as the severity passes 0, 0.15, 0.3 … (so one fire at 85 %, three at 65 %, all at 20 %), and each flame grows from 70 % to its full size, which is 12 % of the building's width (0.5–2.2 m). The spots are picked once per building, seeded by its entity id: 32 points spread over the inner plan of the model are dropped onto its own mesh from above, only those on the upper 60 % of its height are kept, and the spots are chosen apart from each other. They never move. When a heavy blow lands, the severity flares up over half a second. A repair lets it die down over about a second, and the spots go out in reverse order. A destroyed building, or one out of sight, has none (destruction has its own effect).
- **Earlier, larger and on every building** (2026-10-19, after Jiri reported damaged buildings that showed no damage — review: visible): the fires first started below 75 %, a new flame at 45 % of its size and a flame at 75–125 % by severity, so a building at 76–99 % showed nothing and one at 50–70 % only one or two flickers that vanish at game zoom on the large, dark beetle buildings. Now they start below 90 %, a new flame at 70 % and a flame at 85–125 % by severity (the worst fire is as large as before). When more spots burn than are drawn, every burning building's first spot is drawn before any building's second, the nearest first, so a building away from the eye never loses all its fires to a nearer one. [Before and after](captures/damage-fx/): `beetles-85`, `-65`, `-45` (`-before`, `-after`: every beetle building on the beetle bench at that health), `echo-lodge-58` (a War Lodge at 58 % in a beetles-against-ants skirmish on Echo Isles, tick 32400, player 1's view) and `ants-65-after`.
- **Fire look** (iterated with Jiri: no large smooth teardrops, no dark cloud): every spot has a flickering additive glow at its base and 24 short licks (0.26–0.52 s each, varied sizes, re-seeded every cycle). Each lick is a procedural tongue whose edge is torn by noise that streams upwards, with a hot yellow core and orange-to-red tips, in HDR so the roots bloom. The flames are drawn after every other effect, so smoke never dims them. Smoke is deliberately light (Jiri: "super toned down"): 8 small, light grey wisps per spot (22–42 % opacity) rise from the flames and lean downwind, with one fixed wind for all fires. They get a little darker and denser toward low health but never cover the building. One small flickering point light goes to the worst fire near the eye when it is at severity 0.6 or more (below about 39 % health) and an effect light is left after the spells.
- **Hit dust** (`live.rs`): every melee blow that takes health throws a puff of 14 earthy dust particles (0.5, 0.4, 0.28 linear, unlit, normal blend) from the struck body's edge that faces the striker, about waist high. The particles are thrown along the striker's facing in a wide fan, a third of them kicked up from the ground. They grow, slow down (drag), settle (never below the ground) and fade over 0.55 s. Heroes and large units throw bigger puffs. Ranged and siege hits make no dust. The old hit sparks stay as they were; at 4–6 cm they are hardly visible at game zoom. (review: visible — the tint is fixed, not taken from the ground)
- **Budgets**: fires and dust are not cues. The presenter keeps at most 512 fire spots and 256 dust bursts. Every frame the render thread draws the nearest to the eye, at most 28 fire spots (26 flame and 8 smoke parts each) and 64 dust bursts (14 parts each), within 2,048 parts and only from what the cues left: spells are evaluated first and always win. At most 1 of the 4 effect lights goes to fires. Worst case: 120 emitters (of 2,048) and 1,848 parts (of 16,384).
- **Dev tool**: `canopy shot --damage <percent>[,<percent>…]` sets every built building (not deposits or mines) to those shares of its health in turn before the captured tick.
- **Measured** (M4 Max, 1080p, `just bench-render --scenes crowd,default`; other builds were running on this machine, so expect about ±0.5 ms of noise): the crowd battle takes 3.07 ms a frame against 3.12 ms before (draws ±1, same triangles), and 3.02 ms with every building in that scene at 20 % health. The default base view takes 2.2–2.6 ms with or without the change, and 2.28 ms with the base burning at 20 % (3 more draws). Render-thread CPU for the live scene (interpolation, effects, world UI) stays at 0.04–0.08 ms a frame. On the simulation thread, the cost is one mesh hull per burning building model, loaded once, and 32 ray casts per building when it first burns.

## D51. Movement steers like StarCraft II (2026-10-16, Jiri asked for it — review: felt)

Jiri asked for movement as crisp and fluid as StarCraft II's. The old game's movement (carried over 1:1) made a unit face its waypoint before moving, treated every step as allowed or blocked, reserved grid cells, and resolved every contact by waiting, negotiating or detouring: groups stuttered, stalled in gaps and fought over destination points. Research (Blizzard's shipped SC2 unit data, the GDC 2011 navigation talk via summaries, 0 A.D.'s deterministic pushing, Game AI Pro chapters on flow fields and RVO; ZeroSpace's patch notes) points to the same few rules, now in `movement/steer.rs`:

- **No stop to turn.** A unit moves the tick it has a route and turns while moving (SC2 ground units accelerate and turn effectively instantly). Paths stay the existing smoothed any-angle routes; each tick the unit also skips to the next waypoint once it is in sight.
- **Soft spacing, early sidestep.** Neighbours closer than touching plus 0.1 cell push a unit apart (half as hard for allies on the move). Bodies ahead within about a quarter second of travel are eased around; oncoming ones always on the mover's preferred side, so opposing files pass like traffic lanes. Allies walking the same way and pushable idle allies are not avoided.
- **Swerve, push, then negotiate.** A blocked straight step tries 22°, 45°, 68° and 90° turns, the preferred side first. Idle allies in the way (not ordered, fighting, working, held or casting) are shoved aside — sideways first, forward only if both sides are blocked — by at most the mover's step, never into terrain or another body (SC2's push priority). Held up by bodies for 12 ticks (progress means getting closer to the waypoint, not shuffling), a unit may slip past allies coming the other way (SC2's squishy jams; separation spreads them after) and shove them sideways, and falls back on the old negotiation (pocket, local detour, idle ally asked aside); after 40 ticks it plans a new route around bodies.
- **Group arrival.** On a move order, a unit near its goal (3 cells plus three radii) that touches an ally already standing there, or whose way onto its spot is blocked by the group, stops there (`Unit.settled`, which completes the order); within its own radius of the spot it never circles. Other routes (work, pursuit, strolls, separation) always end on their spot.
- **Terrain changes.** A building across the straight way to the waypoint replans at once (at most every 20 ticks).

Consequences: allies on the move may overlap briefly while squeezing past each other in a jam; never a standing body, an enemy or terrain. Exact timings changed where units used to stop to turn (duels a few ticks earlier, workers' mining cycle about 11% faster). The old route follower is gone; the negotiation code stays as the jam fallback. `crates/sim/tests/movement_feel.rs` measures the feel (arrival, stalled ticks, direction jerks, overlap) on six scenarios; before → after: a 25-unit chokepoint never finished (2 stuck, 2,974 stalled ticks, 228 jerks) → 14.7 s (6, 18); two groups crossing never finished (3 stuck) → 14.6 s; walking through idle allies 21.6 s → 13.6 s; open ground 84 stalled ticks → 0.

## D52. AI fixes: wounded units, staging point, attack readiness, grouped reinforcements (2026-10-16, Jiri asked — review)

Jiri saw the AI clump in its base and attack without waiting for a bigger army. Watching AI-versus-AI matches showed why: units below the retreat health (28 %) left the army for good — and nothing heals in this game, so 5–12 wounded units stood idle at the hall door for the rest of the match, while the army went out short-handed.

- **Wounded units are pulled out only while they fight** (a hostile within 14 cells), sent to the staging point; away from fighting they stay in the army. Idle army units in the base dropped from 5–12 to the two home guards.
- **A staging point** 12 cells out of the base towards the nearest known enemy building (else the map's centre, at most halfway) is where the army regroups, withdraws to and where reinforcements gather; the home guard stands 6 cells out, not on the hall's doorstep.
- **Attack readiness**: enough units for the stage of the match (the content's minimum plus one a minute, up to half the maximum) and 1.2 × the power of the enemy army seen near the target in the last minute; after 20 minutes the numbers alone decide, and an army at three fifths of the maximum goes regardless.
- **Reinforcements** go out three or more at a time (or at once when the army fights near home) instead of walking alone into the enemy.

Measured on both shipped maps with four seeds each (AI duels, one hour cap): matches that end now end sooner (mean 28.7 game minutes, from 37–39), as the AI fights with its whole army; two of eight still reach the cap, as one or two of eight did before these changes and before D51 — a stalemate between two large armies, left for later.

## D56. Maps may keep a border nobody enters (2026-10-17, Jiri asked for it)

## D57. The AI never freezes in place; wedged bodies step free (2026-10-17, Jiri asked — review)

Jiri saw the AI "glitch and get stuck in base". Watching AI duels found five causes:

- **One member froze the army.** The safe point a squad is sent to (`Frame::nearest_safe`, old `nearestSafe`) had to be reachable by every member, and otherwise was where the first member stood. A member the AI could not route (wedged, boxed in, or a route its knowledge could not prove) sent the whole army to where it already stood, accepted every beat, for 20 minutes and more. Now bodies that cannot step off their spot are left out, the widest body on ground connected to the point leads, and the point is the nearest one everybody reaches, else the one most reach among the first four the lead reaches, else the nearest open point for movement's pathfinder to try. The failed searches also made AI matches four to five times slower.
- **Stalls were not noticed.** An operation counted as progressing while the squad's centre moved 3 cells, which shuffling and joining reinforcements always do, and its "destination" could be the squad's own position. Progress is now getting closer to the operation's point, or fighting on the way; a stalled target waits 40 seconds before it is chosen again, and buildings on ground the base does not connect to are no target.
- **Empty camps looped.** A camp seen empty before its operation began counted as done at once, was chosen again at the next strategy beat (every 5 s), and every restart began with assembling at home. Only a sighting after the operation began ends it now.
- **Late armies waited for numbers they would never have.** After 20 minutes the attack waited for 22 units, while the economy trains only up to its own army target (which follows the workers) or cannot afford more; such AIs farmed camps for the rest of the match. Late on, an army at its economy's target or with nothing in training goes with at least the minimum when 1.2 × the power of the enemy army seen near the target, as before 20 minutes.
- **Bodies wedged across cliff edges** (simulation, both players; review: felt). The terrain sweep forbids crossing a step too high to climb but not standing across one, so a wide body sliding along a cliff beside a ramp (Amberleaf Crossing's base ramps) could end up straddling it, where every route start crosses the step: the unit stood there for the rest of the match. When terrain alone stops every route from starting, the unit steps to the nearest free cell centre within two cells where it stands on one level (a hop of usually less than a cell, once).

Also: badly wounded soldiers fall back to the staging point (D52), not to the hall's door.

| Echo Isles | 22 → 24 | 21.7 → 22.0 | 23.6 → 22.0 | 10–12 → 8–16 |

## D58. Neutral creeps grow with their level (2026-10-17, Jiri asked for it — review: visible)

As in Warcraft III, a creep's size says how strong it is: the weakest are about a Warrior's size, stronger ones are bigger, and the strongest are as large as a dragon. The creeps' scales had been set one by one (every one `modelScale` 1.7), so level 1 creeps stood half a Warrior's height and the level 9 ones 1.5×.

- **Size by level.** A creep's size, the average of its rendered height and footprint (rest bounds × `modelScale`), is the Warrior's (4.7) × (1 + 1.4 × (level − 1) / 8): level 1 1×, level 3 1.35×, level 4 1.5×, level 6 1.9×, level 7 2×, level 9 2.4× (above the heroes' 2×).
- **Bodies follow** (simulation, review: felt): radius 1.5 × the same factor, as the Warrior's 1.5 at level 1, at most 3.0 (the Marshal's, so the largest still fit the lanes maps keep for heroes); formation spacing 13/6 of the radius, as player units; height the rendered height. Creep bodies had been 0.5–2.3, smaller than any player unit's, and not ordered by level.
- **Camps made room.** The start refuses overlapping bodies, so camps laid out for the old ones no longer loaded. `canopy_sim::spawn::untangle` moves a map's units that overlap a building, a standing resource (trees included) or another body to the nearest clear cell centre, the earlier ones keeping their spot; it ran once over every shipped map (`cargo run --release -p canopy-sim --example untangle_maps -- --data .`: creeps moved a cell or two) and now runs in the Warcraft importer after its fit pass. The map editor's Camp tool sets its ring from the members' bodies.
- Shapes still differ: a round creep (the Violet Sporeling) reads heavier than a tall thin one of the same level.

## D60. Replays, as StarCraft II keeps them (2026-10-17, Jiri asked for it; ships in 0.3.7 — review: visible)

Every match is recorded and can be saved, listed, watched with a timeline and attached to feedback ([ui §Replays](ui.md#replays)). The simulation is deterministic (D4), so a replay is the match's start and the commands its session handed the world; computer players decide again on playback.

- **Recorded where the world executes commands.** The simulation thread hands the recorder (`replay/record.rs`) each turn `Session::advance` applied, after the step, with `World::fingerprint()` every 400 ticks (10 s). Local and remote humans' commands alike (multiplayer included), never the computer players' and never chat. Missions use the same path (their Lua is deterministic, D5, and its progress is in the state), so they are recorded too; no mission map is shipped yet, so none has been played back. A match continued from a save starts from that save. Test in game (the editor's content) and the measured scenes (`--crowd`, `--gallery`, encounters) are not recorded.
- **The file** (`.utcr`, `replay/format.rs`): `UTCR`, a format version, then a gzip JSON header the list reads alone (game version, simulation ABI, time, mode, map name, the map and content identity of saves, start and end tick, players with race, hero, team and colour, who recorded it, the ending and a result word) and a gzip JSON body (setup, the starting save when there is one, the lobby's colours, the commands, the fingerprints, and a map package the game does not ship: its identity files, so the replay plays anywhere). JSON for the reason saves use it (D38). A newer format version is refused by name. Measured: a 20-minute four-player match on Lost Temple (one player's commands sent through a local session, 2,672 commands) is 19.5 KB; an 11-minute duel on Echo Isles (898 commands) 7.1 KB.
- **Where** (D6): `Under the Canopy/Replays` in the player's documents (`Paths::replays`, the `directories` crate's documents folder; the user folder's `replays` without one), so players find and share them. A replay's name is its file name.
- **Saving**: the result screen's **Save replay** writes `<Map> <date> <time> <result>`; renaming happens in the list. The last match is always kept as **Last match**, overwritten whenever a match ends, is left, restarted or the game closes, so none is lost. (review: Claude's call)
- **Replays screen** from the Skirmish screen: newest first, map, date, length, players, result; details with every player's race, hero, team and colour; Watch, Rename, Delete (confirmed), Show in Finder. Replays this game cannot play are listed dimmed with the reason (`Recorded in 0.3.5`, other content, a missing or changed map). (review: visible)
- **The viewer** is an observer match driven by the replay (`sim::Driver::Replay`): a bar along the top with every player's colour, goods, supply and first hero's level; **Statistics** (Tab) opens a panel with tabs Resources (stored and income per minute, gathered, supply, workers), Army (army units and their value, workers, buildings, heroes' levels, supply), Units lost (units and buildings lost and killed, with their value) and Production (what every player's buildings make or research, with progress). The transport sits above the HUD dock: play and pause (Space), time, a timeline to click or drag (the part the background analysis has reached is lighter; the out of sync point is marked), speeds ½× to 8×, and **Vision**: everyone, or one player's fog of war (the debug overlay's reveal and perspective, as a control). ←/→ skip 10 s, so the arrow keys do not pan in replays. Leaving returns to the replays. The observer panel gives way to the replay's statistics. (review: visible, felt)
- **Kills need the killer**: `abilities::Events` keeps a cosmetic death log (who died, whose it was, who struck the lethal blow), never saved, so the panel can count kills per player; deaths without a lethal blow count only as losses.
- **Seeking.** A background thread plays the replay headless as it opens, checks every fingerprint and keeps the world's save with the tally every 200 ticks (5 s), compressed; past 160 MB of keyframes every other one goes and the spacing doubles. A seek moves the shown world to the keyframe at or before the target with the new `World::rewind`, which keeps what the world built from the map and syncs its spatial model and the AI players' navigation to the saved state as after any tick, then simulates to the target without presenting. Where simulating the rest would take over 200 ms (crowded late games cost 3 ms a tick) the seek lands on the keyframe instead, at most one spacing early, finer than the timeline can point. `World::rewind` was added to the simulation for this: 14 ms instead of 204 ms for a full restore on a two-player Echo Isles match, 46 ms instead of 708 ms with four players on Lost Temple; a rewound world plays on identically to a restored one (`crates/sim/tests/rewind.rs`, and `--verify` plays on after its seeks against every fingerprint). Measured on an M4 Max (`canopy replay --verify`): typical seeks 11–85 ms (median 42 ms) on the duel, 160–235 ms (median 176 ms) on the four-player match, where decompressing a 23 MB save takes most of it; a base M1 should be about 1.7× slower. (review: performance against memory)
- **Out of sync**: a fingerprint that differs from the recorded one (from the background analysis or playback) shows "This replay is out of sync from mm:ss" above the transport and is logged; the replay plays on.
- **Feedback** (D59) from a match attaches the replay so far and an exported save of the moment (`.utcsave`, as Export writes it), encoded on a worker thread; the form says "Replay of this match is attached". Watching a replay, the replay itself is attached. Multiplayer matches have no save. The server takes `replay` (≤ 1 MB) and `save` (≤ 4 MB), uploads both to the Linear issue and links them ([server §Feedback](server.md#feedback)); its body limit is 10 MB (Nginx 11 MB).
- **Developers**: `canopy replay <file>` (`just replay`) watches one; `--verify` plays it headless, checks fingerprints and outcome, times seeks and fails when it does not reproduce; `--record <map> [--ticks n]` records a stand-in match (a computer player's commands sent as a human's) for measurements.

## D62. No tree felling; two resources, one of them out in the world (2026-10-18, Jiri)

Trees stop being a resource. Every piece of vegetation, from colossal trunks to small trees and ferns, is decoration that sells the scale (D61); nothing in the environment is cut down or broken. Why: at insect scale, felling a tree breaks the fiction; most players find two resources easier than three; the AI no longer reasons about tree lines; and maps get easier to design, because tree walls become permanent terrain.

The economy becomes two resources:
- **Amber** at the base pays for everything basic.
- **Root**, from Corrupted Root sites out in the world, which players must go out to take.

**Root** is gathered (Jiri, 2026-10-18):
- **Same system as amber.** The same workers from the main hall carry it to a Rootworks.
- **It gates progress**: what lifts a player past the early game costs root.
- **About two workers per site** saturate it.
- **Sites:** maps place a few root sites that are relatively safe and close to the bases. Bigger armies need more sites held further out.

**Amber runs out**, like a Warcraft III gold mine: each deposit holds a finite amount, so players must expand to new amber sites. **Root never runs out**: a held site keeps paying, so the fight is over holding sites, not draining them.

Wood and its costs go away. The engine keeps felling for now (content is input); the base game simply stops using it.

**Tree walls are solid**: no unit passes through vegetation that forms a wall, so players never have to think about it.

**Root is renamed Substance** (Jiri, 2026-10-18, a working name): the forest's raw magic (D66). Players see "Substance"; content ids keep `root` until the name settles.

**A Substance Well is built on top of the site** (Jiri, 2026-10-18, to design and build): instead of a drop-off building placed near a deposit, each race builds its Substance Well directly on the deposit, as StarCraft's refineries sit on geysers. Players read it at once: this is where substance comes from. For beetles the well is the Rootworks' role, and a network source (D66).

**Built, 2026-10-18 (decided while Jiri was away — review: felt)**:
- **Engine.** A building may declare `placementOn: {source}`: it is placed exactly on a seen, standing resource of `source` nobody has built on (the ghost snaps onto the nearest one under the cursor; footprints must be equal, a content rule), skips the ground rules there (the map placed the deposit) and keeps only its doorway check. A harvested building's `harvesting` may say `needsBuilding: true` (gathered only through a finished building on it, and only by that building's owner; others' gather orders are refused, and a worker's job ends when the well falls or changes hands) and `endless: true` (loads never lower its amount). A gather order on the well gathers the deposit under it. The deposit is never touched: when the well falls it stands as it was and can be built on again. The deposit under a well is neither drawn nor picked (`View::covered`); the well's workforce label shows the deposit's gatherers.
- **The well is the drop-off** for Substance, not the main hall: deposits stand out between the bases, and "about two workers saturate it" only holds when the load goes straight in. Two workers gather at once (10 Substance per 10 s each), a third waits: about 120 a minute per well. The well costs 150 amber, 8×8 cells (the deposit's footprint), and the Rootworks are gone: `building.ants.substance-well` (stand-in model: the ants Rootworks) and `building.beetles.substance-well` (stand-in: the beetle Rootworks' placeholder). The deposit keeps its id `building.neutral.corrupted-root` and is shown as "Substance Deposit".
- **Wood leaves every cost.** Basic things (no prerequisite: tier-1 units and buildings, heroes, tier-1 research, starting stock) pay half their old wood in amber more (rounded to 5); progress (hall upgrades and everything that needs tier 2) pays its old wood in Substance instead, on top of any Substance it already cost: the first hall upgrade is 450 amber and 200 Substance, the second 600 and 250. Serrated Tools (felling speed only) is gone for both races.
- **Trees are scenery that blocks.** The tree scenery pieces lose `harvesting` and gain an elliptical `blocker` about the old collision disc (radius 2 cells at scale 1), so tree walls stay solid and unbuildable. `item.wood` and `resource.forest.tree` are gone from the base package; the engine keeps felling and planting for content that wants it. The map editor's tree brush now offers foliage tree models with a blocker.
- **The AI** builds a well once it has a small army (four soldiers): on the nearest deposit it can walk to that nobody holds and no enemy is seen near, sending a worker ahead when the deposit is out of sight, and one more well for every ten soldiers, so farther, contested deposits follow. It staffs each with its recommended two workers and spends Substance through the content's costs. A colony left without a well breaks the least-guarded enemy well once its army matches what was seen guarding it. Measured with `ai_duels` on Echo Isles (ants mirror, eight seeds): every player built at least one well, all eight matches ended (mean 20 game minutes). AI players still never mine a second amber site, so late matches run out of amber with Substance left over.
- **Echo Isles** has two deposits, a mirrored pair between the starts at (259.5, 247.5) and (359.5, 247.5): 144 cells from the nearer start, 243 from the farther, on open flat ground, footprints on the lattice. **The other skirmish maps** had no deposits, so nothing past the early game could be bought there: each start got one deposit, picked by a search (open, dry, flat ground every start can walk to, 40–80 cells out towards the middle of the starts, nearer its own start than any other by half again, 20 cells from camps and 16 from amber sites), as D62's "relatively safe and close to the bases". These are placeholders for a design pass per map (review: visible).

**Wells pump by themselves** (Jiri, 2026-10-19: "Substance extractors should work autonomously — no worker should be needed, for any race"; built by Claude — review: felt). A finished Substance Well now makes 10 Substance every 5 seconds into its owner's stock, about the old saturated rate of 120 a minute, with no workers; the deposit takes none.
- **Engine.** A generic building field `income: {item, amount, intervalTicks}` (a currency): while the building stands complete and alive, held by a player, and powered if it needs power (D66), it counts ticks on the entity (saved, so saves and replays resume it exactly) and pays every interval, in id order; unpowered it holds its count, like training. Each payment is a `Produced` fact ("Income", in the accounting) and a delivery for presentation. A building with income works (D65 `work`: the beetle well's column and arcs run whenever it pumps), and its card says "+10 Substance every 5 s". Tests: `crates/sim/tests/economy_income.rs`, and `ai_economy.rs` (a colony builds a pumping well and sends nobody to it), on test-owned content.
- **Content.** Both wells carry `income: {item.root, 10, 200}`; the workers (`unit.ants.settler`, `unit.beetles.worker`) no longer harvest `item.root`, and the deposit's `harvesting` asks for no workers (`recommendedWorkers: 0`), so there is no second income and the well shows no workforce. The deposit keeps `needsBuilding` and `endless`: content whose workers do harvest through a well still works as before.
- **The AI** needs no well staffing: its gathering already staffs only what its workers can harvest. It still builds, defends, rebuilds and contests wells as above. `ai_duels` on Echo Isles, four seeds each way: beetles (seat 1) against ants, before 4 of 4 finished, ants won all, mean 19.7 min, beetle Substance income 420–840 a match; after 4 of 4, ants won 3, mean 21.8 min, beetle Substance 880–3,210. Ants (seat 1) against beetles, before 3 of 4 finished (one ran to the 60-minute cap), ants won all 3 (mean 17.2 min); after 4 of 4, ants won all, mean 24.2 min, beetle Substance 520–2,050 (was 0–340).

## D63. Renderer additions for the forest floor (2026-10-18, Jiri asked to build it — review: visible)

Three renderer changes, made while bringing the fall look-dev map (`base/maps/showcase/lookdev-fall.utcm`) towards its target frame (`art/styles/target-fall-lookdev.jpg`, docs/art-direction.md):
- **Ground clutter casts shadows.** Scenery now casts a shadow from 0.2 m of height (`STATIC_SHADOW_MIN_HEIGHT`), down from the old 0.75 m, so curled leaves, acorns and fern sprigs read as depth from the play camera. Live models keep 0.75 m. Shipped maps with low foliage get more small shadows. Cost on the look-dev map (16k instances, M4 Max): the shadow pass rose from 0.2 to about 0.9 ms. (review: visible)
- **Foliage varies per instance.** Every instance of a foliage material gets its own value (±18 %) and warmth from a hash of where it stands, so a field of one leaf or fern model doesn't read as a pattern. It is in `statics.wgsl` (`foliage_variation`); units and buildings are untouched. (review: visible)
- **A map may paint a frame shade.** `terrain/shade.grid` (optional, f32 per vertex, 0 lit to 1 black) darkens every forward surface where it is painted, via `frame_shade` in `scene_out`. It is how a map keeps its non-playable frame below its playable ground (the army-first rule of D61). The map format reads and writes it when present; maps without one are unchanged.
- **A map may paint its frame.** `terrain.overlay` (`{asset, x, z, width, height}` in metres) lays one large unique image, a texture asset with premultiplied alpha, over the ground layers in that rectangle (`ground_at` in `terrain.wgsl`). The look-dev map's is a gpt-image painting of the forest floor, cut to the map's frame by `tools/terrain/build_overlay.py`, so the frame reads as painted detail without thousands of props. Cost: one texture fetch per terrain pixel inside the rectangle. Maps without one are unchanged. (review: visible)
- **Water may glint.** A water profile's optional `glint` adds sun glitter: sparse sparkles on the ripples, gathered into drifting runs and faded out when zoomed away, as a stylised stand-in for the sun mirrored in moving water that a top-down camera never sees. Profiles without it are unchanged. (review: visible)

Not done yet, from the same comparison: specular glints on wet ground, and a reflection term for still water. The third-person camera shows the world beyond the unit's sight in the fog of war's grey.

## D64. The canopy: one world, two cameras (2026-10-18, Jiri asked for it — review: visible)

Jiri's notes: god rays are for the third-person view (J), and in the RTS view they are a tiny effect at most; the RTS view is about moving shade. Beams should fall from above, not slant in from the side. The distant forest in J needs depth of field. The giants should not shade the playable ground. Optimisation waits until the direction is settled.

The renderer now knows how close to the horizon a camera looks: the **view fade** (0 at RTS pitches, 1 for close cameras; `surroundings::view_fade`, in the frame uniform's `background.w`). What changes with it:
- **Light shafts.** A biome's `atmosphere.overheadStrength` (0–1, default 1) is the share of haze and shafts kept at RTS pitches; the autumn forest keeps 8 %. In close views the haze marches up to 420 m and through the sky. `atmosphere.shaftElevation` (degrees, optional) gives the beams their own steep direction along the sun's bearing, so they fall from the canopy's gaps under a low evening sun; such beams follow the gaps alone, sharpened into separate columns, not the low sun's shadow map. The haze's upsampling and filter now weigh depth differences relative to the distance, and anything past 4 km counts as sky (resolved edge pixels average a surface with the background), which removed bright ghosts and dark specks around trunks seen against the forest. (review: visible)
- **Depth of field** for close cameras: sharp to 40 m, fully soft from 260 m, a 24-tap disk weighted by each tap's own blur so the foreground never smears. The disk turns per pixel and bright taps count less (a Karis average): a fixed disk stamped every bright point into the same 20 copies, which read as a grid over the screen. Off at RTS pitches. (review: visible)
- **Giants above the RTS view.** Scenery with the `canopy` capability dissolves above 75 m over its base at RTS pitches (as the surroundings' trunks always did) and casts no shadow above 75 m at all: whole trees can rise into the canopy for close cameras without covering the map from above or blotching the playable ground with crown shadows. Their boles keep their long shadows. Existing canopy models are under 75 m. (review: visible)
- **Close cameras see 1,600 m** (was 180 m), so the surrounding forest stands on the horizon. Beyond the map the fog of war fades to lit over 48 m: nobody can explore there, and the surroundings were black in J.
- **Ambient motes** (`motes.rs`, a biome's optional `motes`): dust that glints only in the canopy's light, for close cameras, and leaves tumbling down around the view in every camera. The dust floats 4–32 m ahead of the camera, in front of the depth of field, and each mote is one or two pixels at any distance: larger or blurred motes read as light bulbs. The shafts' reach for close cameras is 260 m, and the autumn forest's beams are thin (shaft density 0.0035), so the forest stays visible through them. Generated on the GPU from the instance index in fields that wrap around the camera: no buffers, two draws. (review: visible)
- **Shots reveal sandbox maps** for their player, as the game does, so `canopy shot --play` shows what a player sees.

Art for it: `tools/props/build_tree.py` dresses a bare Tripo tree (decimated by `import_tripo.py`, from about 2 M to 30k triangles) with gpt-image leaf-spray cards on its upper limbs, alpha-masked foliage with flutter pivots and wind, so the crowns sway and let light through. The look-dev map has giant oaks and beeches (170 and 220 m) around the clearing and beyond the map, and 20 m autumn saplings in the frame. Cost on the look-dev map (M4 Max, 1080p, High): about 4.3 ms frame to idle in the RTS view, up from 3.1 ms; level of detail and shadow budgets for the giants come with the optimisation pass.

## D65. Buildings at work: motion means something is happening (2026-10-18, Jiri asked to build it — review: visible)

A building at rest holds still: no animation, no glow, no smoke. The moment it trains, researches, upgrades or revives, it comes alive, so motion is the signal that something happens (Jiri's rule). Built first for the beetles' Shell Forge (`art/styles/forge-idle.png`, `forge-work.png`), reviewed on `base/maps/showcase/beetle-bench.utcm`.
- **A public busy signal.** The simulation's public work view of a building now carries `busy` (training, researching, upgrading or reviving, and not paused, blocked or under construction) and `cycles` (finished training cycles). Everyone who sees the building sees that it works, never what it makes or how far along it is, as in Warcraft III. A remembered building (fog) rests. (review: felt)
- **Building states.** Buildings get an animator (`BuildingAnimation`): `idle` is the rest pose (a still clip), `work` loops while busy, `spawn` plays once when a cycle finishes, fading in and out over 0.45 s of clip time. Clip events (seconds into the clip, like units') are reported each tick. Animated building models keep the building material (rigid node animation, not skins), and their sockets resolve for effects.
- **State effects.** A building definition's `presentation.effects` lists `{effect, state | event, socket}`: an effect loops for as long as the building is in a state (`work`, `spawn`) and stops when it leaves it, or plays once on a clip event (the forge's `strike` throws sparks). Sockets are model nodes named `socket*`.
- **Active glow.** A material's `activeGlow` extra (`{pulse, flow}`) makes its emission alive only while its model works: scaled by the instance's activity (easing in and out over half a second), pulsing, optionally streaming along V. Scenery never works, so its active emission stays dark. The pack format is version 3.
- **Effect lights:** 8 at once (was 4), so a working forge's firelight does not starve spell flashes.
- **Building size** (Jiri): buildings have no walkable perimeter, their models fill their footprint. Sizes follow Warcraft III's tile ratios against the main hall (Town Hall 6×6 with its buffer, Blacksmith 5×5): the 20-cell main hall, a 16-cell upgrade building (the Shell Forge, was 12). (review: visible)
- **No dirt under buildings** (Jiri): models carry no ground, dirt or earth skirt; the map's ground is the ground. It starts at the concepts and Tripo references, which show clean bases on a plain floor; the Shell Forge's Tripo skirt is cut away (`kit.strip_dirt`). (review: visible)
- **Forest magic is blue-purple** (Jiri): contained and living magic in buildings (the forge's quench tank, the Rootworks' sap) glows blue to violet, never green; fire stays orange. (review: visible)

Art pipeline for it (Jiri: base models come from Tripo, never invented): gpt-image concept per state → Tripo image to 3D of the idle concept → Tripo segmentation into parts → `tools/buildings/<building>.py` in Blender (team mask from the blue plates into each part's base-colour alpha, active glow from the dark interior texels of the glowing parts, moving parts as their own nodes with Euler clips, sockets) → `tools/buildings/kit.py` exports clips as actions (glTF imports use quaternions; meshes with textured materials need UVs or the exporter writes −1). The whole pipeline, for any agent, is the `canopy-buildings` skill.

**Amendment: units, rest and gathering at work** (2026-10-19, overnight while Jiri slept, for the beetle machines — review: visible). The beetle units and buildings needed more of D65 than buildings at work:
- **Unit effects.** `presentation.effects` plays for units too, with the same socket resolution (a declared socket name or a `socket*` node): event effects on any clip event of the current state (a Bombard's blast on its attack's `release` at `socket_muzzle`, a Juggernaut's dust on `step` in `walk`), and looping effects while the unit is in a state: `move` (walk, run, carry or charge), `attack`, `cast` (any cast), `idle`, `always` or an engine animation state. Looping effects follow their socket as the model moves; their particles move with it (stateless effects, as statuses on moving units). Events are reported once per crossing, also when an attack clip is sampled to the impact tick. Content validation checks the state against the kind, the effect id and the socket's form.
- **Rest and always.** Buildings gain `idle` (resting, complete) and `always` (complete and in sight). A building without clips still rests and works for its effects and glow, and its sockets resolve at rest, so a neutral deposit can carry rising motes.
- **Gathered buildings work.** The public `busy` signal is also true while workers are assigned to a building as a harvest site (D62's Substance Well pumps while gathered: on the wells branch its `site` is the deposit's workforce). Presentation-only data in the view; the simulation is unchanged.
- **Unit activity.** Units have an activity like buildings, 1 while they move, fight, cast or work, eased over about 0.4 s, so a machine's `activeGlow` furnace pulses while it works.
- **The light budget.** Looping state effects of buildings and units hold at most 5 of the 8 effect lights; spells and impacts keep the other 3 (`effects::AMBIENT_LIGHTS`). (Claude's call)
- **Stride-matched gaits.** A gait whose animation declares `nominalSpeed` (model metres per second at rate 1) plays at the measured ground speed ÷ (`nominalSpeed` × drawn scale), within 0.4–3×; other clips keep the old 1.5×, so the ants are unchanged. The speed is measured from the presented positions, smoothed. (Claude's call)

## D66. Beetles build on a substance network (2026-10-18, Jiri — review: felt)

The forest runs on **substance**, its magic, and each race relates to it differently. Ants use it directly and it changes their bodies. Bees transform with it through blood and ritual. Beetles never take it in: they use it only through technology, which is fully powered by it and depends on it. Their bodies stay plain chitin; substance shows only inside their machines (glass tanks, coils, canisters, exhaust), blue to violet (D65). Getting stronger is a better machine, never a mutation. Race design is a clean slate: the ant roster was a test and constrains nothing. Root (D62) is the raw substance tapped from the world.

**The network**, StarCraft's pylon power made beetle plumbing. It decides where beetles build and which buildings work, never how strong a unit is in a fight (a positional combat bonus was rejected as unbalanceable).
- **Sources and nodes.** The beetle main hall and the Rootworks are sources. The **Brood Den** is the node: it gives supply and extends the network, with a **generous radius**, well beyond a pylon's few cells.
- **Placement.** Every other beetle building must be placed inside the network.
- **Unpowered buildings stop working.** Production and research pause until power returns. The building stays standing.
- **Towers need power** and are clearly stronger than other races' towers, to offset not being able to push them forward for harassment.
- **No pipes are drawn.** The network shows as an overlay only while a building is being placed (or when the grid is shown).
- **Open:** whether dens must chain to the network or can stand alone, and any further race mechanic. To be settled when the network is designed.

**Implemented** (2026-10-18, overnight while Jiri slept — review: felt, visible). The network is a general engine feature driven by content (`canopy-definitions` skill, "The power network"):
- **Content.** `network: {role: source | node, radius}` and `power: "required"` on building definitions; a research effect's `networkRadius` adds cells to the listed buildings' radius (Pressure Mains). Beetle values: every hall tier a source of 32 cells; the Substance Well (D62) a source of 20 cells that needs no power, so it stands wherever its deposit is and powers ground out there (Claude's call, 2026-10-19, when the wells and the network were merged); the Brood Den a node of 28 cells that needs power; War Lodge, Shell Forge, Hornwatch and Ancestor Shrine need power. Validation: only buildings take part, radii are at least a cell, network research lists only network buildings, and a roster with buildings that need power has a source.
- **Chaining (the open point, Claude's call):** dens chain. A node powers its disc only while its own centre is powered, and it needs power to be placed, so the network grows outward from the halls and wells, a cut den darkens what hung on it, and a lone forward den is impossible. Why: it keeps the network territorial (Jiri's "a fortress race that grows outward"), gives raids a target with a consequence, and is how StarCraft players already read pylons; standalone dens would make placement nearly free and the network meaningless.
- **Coverage** is the building's centre inside a disc (as the overlay shows it); sources and nodes count only when complete and alive.
- **Unpowered buildings** (complete, needing power, outside their owner's network) hold their training, research, upgrade and revival progress, and a lookout's garrison holds its fire; supply stays. They resume where they stopped when power returns. **Construction goes on** outside the network: sites neither power nor need power, so losing a den never wastes a half-built building, and it simply waits dark when done. (Claude's call)
- **Simulation:** `economy/network.rs`, derived from state (never saved): powered discs per owner and the unpowered set, recomputed only when a building that takes part appears, finishes, dies or changes definition, or research completes; integer milli-cells, id order, a fixed point for the chain. Placement (`can_build`), production, research, upgrades, revival and combat planning (garrisons) read it. Tests: `crates/sim/tests/economy_network.rs`, `combat_garrisons.rs`.
- **AI:** it places buildings that need power only where its own network reaches; when no powered site is left it builds its race's cheapest node at the edge of a disc where it adds the most ground, and when a building is cut off it builds a node towards it.
- **Display:** no pipes. While placing a building that needs power (or with the debug overlay's **Show power network**) the network lies on the ground as one soft blue-violet field (an even faint fill, a glow inward from the edge and a crisp rim; overlapping discs do not stack), and the ghost turns red outside it with the message naming the den. An unpowered building's work glow stays dark and a small dark badge with a struck violet bolt floats above it; its card says "Unpowered: outside the network". Captures on the beetle bench: `docs/captures/network/` (placing inside and outside, a chained den, a lodge cut off by a lost den); `canopy shot --play` scripts gained `network` and `destroy:<text>`. (review: visible)

## D73. One queue per building (2026-10-19, Jiri — review: felt)

Jiri: "We need one queue per building." A building's training, research and hero revivals all advanced at once, so a War Lodge researched while it trained at full speed, which neither Warcraft III nor StarCraft allows. Now a building works on one thing at a time, in the order the player queued them (`economy::lane`).

- **Order.** Training and revival entries already took their id from the match's queue counter (training and revival shared a lane before). Research entries now take an `order` from the same counter. A building's head is the smallest of its three queues' heads; only it advances. When it finishes or is cancelled, the next item goes on, whatever its kind. Each kind keeps its own list, each in queued order. A workplace whose queue research leads shows the status "Researching".
- **Unchanged.** An upgrade still holds training, research and revival. Automatic production (planting, a building's own automatic output) is not queued and runs beside the queue. Pausing a workplace pauses its training and revivals as before; research ignores the pause as before.
- **Capacity.** Kept per kind: training and revivals count together against their `queueCapacity` (as before), research against `research.queueCapacity`. One shared capacity would change every building's numbers in content; the separate caps are safe because only the head advances anyway.
- **Saves and replays.** The order lives in the entities, so saves and replay keyframes resume exactly. A save from before has no `order` on research (serde default 0); loading (`World::restore`, `rewind`) numbers such research after everything queued, so it waits for the training queued with it.
- **HUD.** The selected building's panel shows one queue: the working item with progress, then the waiting items as tiles in queued order (training, research and revival mixed), each cancelling on click. The observer panel shows progress only for each building's working item. A building is busy (D65) for research or revival only while that leads its queue.
- **AI.** Research at a building that trains holds its training up, so the AI researches at such a building only with no training queued there and nothing it trains wanted now (army below plan, workers below need) that no other building could train. It queues no training at a building with research queued, and counts a researching barracks as saturated when deciding to add production. Research-only buildings research as before.

## D76. Warcraft-grade effects: curves, world-space particles, soft particles (2026-10-20, Jiri: "make one flagship spell look as good as a Warcraft III spell" — review: visible)

Researched how Warcraft III, StarCraft II / Heroes of the Storm, Diablo, Overwatch, Dota 2, League of Legends and current RTS build spells (report in the session notes; the WC3 data comes from the installed game's own models). Their look comes from a small set of engine tools, not from resolution. Those tools are now in the effect system, all opt-in content fields, proven on Forgefall:
- **World-space particles** (`emitter.space: world`, `inheritVelocity`): particles stay where they were born, so a moving emitter leaves a trail (WC3's Rain of Fire and Inferno work this way). An emitter `rides` a missile or rain layer of its effect, or follows a unit. Stateless as before: the scene samples the emitter's path (32 samples over the live births) into a buffer and the shader finds each particle's birth point on it, so the picture is still a pure function of time.
- **Curves over life** (`colourOverLife`, `opacityOverLife`, `sizeOverLife`, `additiveOverLife`, `erosionOverLife`, `heatOverLife`; up to 8 keys) and over a layer's life (`opacityOverLife`, `scaleOverLife`: a mark that appears, holds and fades). Baked into 32-sample curve blocks the GPU reads once per load.
- **One premultiplied blend with additivity per particle**: fire born glowing turns into smoke that covers; partly covering fire stays saturated on bright sand instead of washing to white (the research's main finding for our ground). `additive` and `normal` layers draw exactly as before.
- **Soft particles**: effects moved out of the forward pass into their own pass over the resolved scene, reading the linear depth every opaque surface already writes; sprites hide behind surfaces and fade over `soft` metres (0.4 by default) where they meet them. Ground decals cut hard. Effects lose MSAA (soft sprites do not show it); the pass costs one load and store of the scene colour and is skipped when no effect shows.
- **Fire shading**: a `ramp` colours a grey texture's brightness (white core, orange body, red rim from one sprite), `heatOverLife` cools it, erosion breaks sprites up from their thin edges. Flipbooks can span a particle's life (`overLife`) and cross-fade (`blend`).
- **Motion**: turbulence (smooth swirling drift), landing on the ground with friction (`collide`), inner cones and ring spawns for flat blast waves, ground streaks along their travel.
- **Ribbon layers**: a textured strip along an emitter's path (scrolling, tiled, colour, opacity, width and additivity over its age).
- **Model rain** keeps the model's authored pose (no tumble) and `intensity` below 1 makes it translucent.
- **Textures**: a small shared grey library (`tools/content/vfx_art.py`: puff, flame strip, ash, debris chunks, blast ring), procedural so its frames and tiling are exact; gpt-image-2 stays for single painted shapes.
- **Forgefall** is the first spell built with them (Jiri's design): a translucent red-hot anvil falls trailing fire, smoke and a flame ribbon that hang in the air; it lands and fades within a third of a second as a blast wave of fire races out over the ground, cools into ember-ash and drifts off, over a dust ring, flung ash, embers and rock, a scorch and a smoke column.
- Not done yet, by agreement: heat distortion, forking lightning, unlit mesh effects with scrolling UVs, camera shake. Rolling the tools out to the other spells waits for Jiri's approval of Forgefall.

## D80. Maps are blocked out in 3D, and the world is generated from the blocks (2026-10-20, Jiri)

Jiri: authoring must be fast for people, not scripts; a campaign needs many maps and camps. A map should be drawn as its shape (cubes you raise, ramps you drop) and everything else generated from it, seeded, so the generator can be polished "to oblivion" and every map gains from it.

- **Blocks.** A map is authored as columns of blocks, **4 × 4 cells** each (the building lattice, so cliffs line up with foundations; 1 × 1 detail may come later), stacked in whole cliff levels (3 m). **2.5D**: one walkable surface per column; overhangs and arches later, as bridges are today. **Diagonal blocks** cut a column along a diagonal so outlines can run at 45°.
- **Cliffs are not drawn**: they are where two columns' levels meet. Ramps, water and impassable ground are kinds of block; landmarks (giant trees, boulders) will be multi-block placeholders.
- **The simulation reads only what the blocks make**: heights, water and closed cells, derived deterministically and saved in the map, so a map plays the same forever. The look will be regenerated from the blocks and a seed at load, never stored.
- **Order**: the blockout editor alone first, to get the feel (this decision's first build); then the generator (ground, cliffs, frame, water dressing); then landmarks and set pieces for the campaign. Echo Isles is converted first.

**The generator, first build (2026-10-20, Jiri: "this scene, built and playable, achievable in editor"; target `art/styles/target-frost-cliff.jpg`).** `canopy_scene::generate` makes the world from a map's blocks and its biome's `blocks` recipe, at load, in the game and in the editor's Generated view (G). Nothing it makes is saved or seen by the simulation.
- **Zones** per cell from distance fields: frame (closed ground) and its edge, open ground and its edge, cliff tops and feet, ramps, ice and its shore. Everything below is placed by zone.
- **Ground**: closed ground's cover in the biome's grass layer with an edge that wanders only inward (what looks impassable is, D71), mounded up (`frameRise`, the look only), shaded (`frameShade`); rubble paint on ramps and along cliffs; ice paint on ice.
- **Cliffs are generated geometry, not a kit of pieces** (Jiri asked whether we need 3D pieces): a mesh along every steep drop, from contours of the heights halfway between levels, so it follows any block outline, diagonals and ramp sides included. It is a talus of stones at about 50° (`slope`), broken into domed stones by cellular noise in world space (so faces join) with dark grooves (per-vertex occlusion), a lip on the plateau and a flared foot; rubble rocks at the foot, on ramps and along tops, boulders heaped on rock blocks, tufts of frosted spikes in frame edges. One textured mesh, triplanar, lit like scenery, casting shadows (`canopy_render::dressing`).
- **Decals**: flat cut-outs (leaves, clover) pressed onto the ground in one instanced draw per atlas, scattered by zone, optionally in clumps and faded under ice (Jiri: the leaves on the ice "should likely be decals"). Atlases are made by `tools/terrain/build_decals.py` from gpt-image sheets.
- **Scenery** scattered by zone from the recipe's lists (roots, ferns, leaves); hand-placed props stay as authored.
- **Frost** (`light.frost`): rime on upward faces of scenery, trees and cliffs; units and buildings stay clean (the army first).
- **Ice** is a block kind: walkable frozen water 0.15 m under its level.
**Second pass (2026-10-21, Jiri drew the scene's setup over the target: a top level ending in a bank of roots, one diagonal ramp, the lower ground at the pond's level, larger decals; "almost everything here is texture", the spikes the one model; texture for surface, models for silhouettes, as ZeroSpace does).**
- **Painted cells**: `terrain/block-paint.grid` paints kinds cell by cell over the columns (levels stay whole columns), so an outline that is only a change of kind, such as a shore, runs at any angle. Jiri's "probably needs 1×1 cells", taken for kinds only: 1 × 1 heights would make a much heavier editor and harder pathing.
- **Ramps are regions**: connected ramp columns of one level and one direction (eight, stored with the cut) fall as one plane, so a ramp can be wide, long and diagonal. The Ramp tool takes the direction from the drag (top to foot) and cuts a diagonal ramp's staircase teeth.
- **Faces**: a column's fourth byte is the face style its cliffs take: 0 the biome's cliff, otherwise one of the recipe's `faces` (Frost Hollow: Roots, a long overhanging talus of roots wandering in and out, generated root tubes across it and spilling past its foot, tufts of pale scaly spires along its top). Faces taper at the ends of their runs; zones near a cliff know its face, so decals and scatter can follow one face.
- **Shore**: a low rim of crusted stones wherever walkable ground meets ice at about its level, along a smoothed outline of the ice (`shore`).
- **Ice is texture**, matte and frozen (roughness 0.72), not water; decal sheets carry their own frost (the shader's rime washed their colour out) and come from transparent gpt-image sheets (Sunburst).
- **Comparison**: `tools/look/compare.py` measures each render against the target region by region; the scene is shot at zoom 0.7, the target's scale.
- **Ground per level** (`levels`): a level can have its own ground (a main's paving, a middle level's moss), blended down ramps by their height. Its material must be one of the biome's layers (painted materials outside them need corner atlases).
- **Frozen Dream** (`base/maps/skirmish/frozen-dream.utcm`, Jiri: "create perfectly looking starcraft map, lets say this one", Ever Dream LE): Liquipedia's map page sits behind a human check, so the layout is drawn after Jiri's picture rather than copied: paved mains (level 3) in opposite corners, one ramp each to a moss shelf (2) holding the natural and third, ramps down to a dusty lowland (1), moss pockets and a moss island, root banks, a frozen forest frame. Authored with block operations alone and point symmetry (`tools/maps/frozen_dream.py`); lanes keep the army's 7 cells.
- **The look-dev scene**: `base/maps/showcase/frost-hollow.utcm`, authored only with block operations through MCP `map_blocks` (`tools/maps/frost_hollow.py`) in the new `frost-hollow` biome; textures cut from crops of the target and remade as tiles by gpt-image (`frost-ground`, `-ice`, `-rubble`, `-litter`, `-stone`). (review: visible)
**Third pass: the Underleaf polish (2026-10-22, Claude's design while Jiri delegated the campaign's look — review: visible).** Generic recipe controls, so any biome dresses real maps richly without per-map work (docs/art-direction.md, Underleaf):
- **Ground patches** (`blocks.patches`): soft noise patches of a ground over walkable ground only (never under the frame's cover), sized in metres, with a share of cover, a soft frayed edge, optional levels and an optional band along the frame. Large, calm variation, as D61 asks of the playable ground.
- **Extra ground layers** (`terrain.extra`): tiled grounds after the biome's six built-in ones, fed only by paint (patches), so a biome is not limited to six materials; at most eight.
- **Scatter in stands**: `groups` (neighbours share a piece), `clump`, `depth` (cells into closed ground) and `grow` (scale follows the depth), for frames of one species per stand, small at the rim and tall deep in (the giants' finding).
- **The giants' shadow ceiling per biome** (`light.shadowCeiling`, D64's 75 m the default; Underleaf 30 m): canopy scenery casts no shadow above it, so caps and crowns never blanket a base while stalks and boles keep their long shadows.
- **Editor**: the viewport hands egui a plain `Rgba8Unorm` view of its sRGB target; through the sRGB view every preview and the Generated view showed decoded, far too dark.
**A map's own frame dressing (2026-10-22, for the campaign's authors: healthy green giants stood round the first mission's sick Hollow; Claude's design, review: visible).** A map may override or extend its biome's frame scatter in its own data, `landscape.scatter` (skill **canopy-maps**): entries of an area (a circle of cells, a mission region, or the whole map), the biome pieces taken out inside (all, or by scenery id) and scatter layers of the biome's own format added inside, the edge blending over `fade` metres along a wandering, dithered line so the change reads as a drift and not a circle. Taking pieces out never moves the biome's others (every candidate draws its randomness before it is dropped), so the rest of a map is unchanged. Layers are kept as JSON in the map (the content crate does not know the renderer's types) and read by the generator, which warns of a layer it cannot read; the map check asks for a zone, pieces and a density. Rejected: per-map biomes (a whole biome for one corner) and hand-placing the frame (it is generated, D80). The Hollow Brood withers 84 cells round its basin (fade 16): no porcini, morels, ferns, clover, sorrel, moss or parasols; withered and bleached mushrooms, dead ferns and withered ground; the leaves, cones and stones of the litter stay.

## D83. A map's weather and time of day; the map editor's one panel (2026-10-21, Jiri)

(review: visible)

## D88.
