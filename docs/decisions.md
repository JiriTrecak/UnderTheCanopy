# Decisions

Decisions that shape the code. Newest last. Each entry says what was decided and why; reverse one by adding a new entry that supersedes it.

## D1. Rust and wgpu, shaders written once (2026-10-14)

The game is Rust on wgpu with WGSL shaders, driving Metal on macOS, DX12 on Windows and Vulkan as fallback. No per-backend shaders or code paths. No engine framework (no Bevy): our own architecture on a few libraries (wgpu, winit, an audio library, taffy, cosmic-text). Why: full control, predictable performance, one renderer everywhere.

## D2. WebGPU feature baseline (2026-10-14)

Devices are created with WebGPU's default limits and only features WebGPU also offers (plus BC texture compression when the cooker needs it). Native-only features are allowed only as optional fast paths with a fallback, and each one is agreed with Jiri first. Why: the editors will embed the same renderer through WASM and WebGPU in phase 2.

## D3. Simulation at 40 Hz on its own thread (2026-10-14)

The simulation ticks every 25 ms on its own thread; the renderer runs at the display rate and interpolates between snapshots. Why: the frozen server and lockstep input delay are built on 25 ms ticks, finer ticks keep commands responsive, gameplay is tuned at this rate, and the cost in Rust is small. The tick length is one constant. Content durations (`*Ticks` fields) are authored in fixed 25 ms units (`AUTHORED_TICK_MS`) and converted to simulation ticks on load, so a different tick rate would not change the data. Parallel work inside a tick merges results in a fixed order.

## D4. Determinism from day one (2026-10-14)

Simulation math uses deterministic functions (`libm` or fixed point), never platform math libraries; iteration orders are fixed; randomness comes only from the simulation's seeded generator. CI runs replay-hash tests on macOS and Windows, and hashes must match. Why: lockstep multiplayer and replays depend on it, and adding it later means rewriting the simulation.

## D5. Lua 5.4 through mlua for scenario scripting (2026-10-14)

Map and campaign scripts run on vendored Lua 5.4 via `mlua` with no standard libraries opened, exactly like the old sandbox: scripts reach only the `mission` API, so platform maths and Lua's own randomness are unreachable, and the unfixed string-hash seed only affects table iteration, which scripts cannot observe. Why: today's scripts target Lua 5.3 (fengari) and run on 5.4 nearly unchanged; Luau would break integer and bitwise semantics. Differences scripts can notice are listed in [simulation](simulation.md#lua).

## D6. Platform layer owns every path (2026-10-14)

No code depends on the working directory. Game data is found at `Contents/Resources/data` in the macOS bundle, `data/` beside the Windows executable, or `--data <folder>` in development; user files live in the OS user-data folder (`com.jt.canopy`). Why: packaging for any platform then needs no code changes.

## D7. Packaging and CI from M0 (2026-10-14)

CI builds, lints, tests and packages on macOS (Apple Silicon) and Windows on every push: an unsigned `.app` and an NSIS installer through `cargo-packager`. Checkouts skip Git LFS. macOS minimum version 13. Why: portability problems surface immediately; signing and installers are added later without code changes; LFS bandwidth is billed.

## D8. Apple Silicon only (2026-10-14)

macOS builds target arm64; no Intel support. The reference (weakest) machine is a base M1 with a 7-core GPU. Why: Intel integrated GPUs would set a far lower budget for little benefit.

## D9. Data mirrored, formats unchanged during phase 1 (2026-10-14)

`content/`, `assets/` and `art/` are mirrored from the old repository with `just sync-data` and keep their formats exactly. `canopy-content` is a strict reader of those formats. Why: the editors stay in the old repository until phase 2, so its output must work here unchanged. Identical binaries in `art/` and `assets/library/` cost nothing extra in LFS (content-addressed).

## D10. Match server and protocol frozen (2026-10-14)

The TypeScript match server stays in the old repository and stays deployed. `canopy-net` implements the client side of its protocol exactly. The server embeds `content/game.json` (races, starting heroes) and action-shape validation, so new races or heroes need the server redeployed with the new content, and new action types need a server change. Why: it works, and porting it adds nothing to the game.

## D11. Profiling built in (2026-10-14)

`tracing` spans everywhere; the `profile` feature streams them and frame marks to Tracy (`just profile`). The `profiling` Cargo profile is release with full symbols. Why: performance claims come from measurements on the reference machine.

## D12. Content validation scope in phase 1 (2026-10-14)

`canopy-content` rejects anything structurally wrong (unknown fields, wrong types, unknown enum values) and enforces every cross-reference and invariant the simulation relies on, matching the old loader's rules. Pure authoring limits (for example a maximum speed of 40) are not duplicated while the old editors still validate the data; they move to Rust with the editors in phase 2. `just parity` compares the Rust reader with the TypeScript loader on the same files. Why: full constraint parity is editor work; the game needs correct reading and sound invariants.

## D13. Sampled multiplayer hash (2026-10-14)

Desync detection keeps the old design: every 8 ticks a cheap fingerprint of the id counters, jobs, stocks, outcome and a rotating sample of at most 32 actors, in the existing `hash` message. A full-state hash is not computed. Why: it is enough to catch desyncs, and hashing everything every few ticks costs too much.

## D14. Fix bugs found in the old simulation (2026-10-14)

"Behaves the same" covers intended gameplay, not defects. Clear bugs found while rebuilding are fixed and noted in the commit and, if players would notice, in the release notes. Changes to how the game plays still go to Jiri first.

## D15. Movement and pathfinding keep the old rules for now (2026-10-14)

Movement, pathfinding, collision and traffic are rebuilt with the same rules and behaviour as the old game, implemented efficiently. A proper redesign (flow fields and more) comes later as its own piece of work.

## D16. New save format (2026-10-14)

No compatibility with the old game's saves; nobody depends on them. The Rust save format is designed fresh.

## D17. Verification by play (2026-10-14)

No automated behaviour comparison against the old game. Correctness comes from scenario and determinism tests, and from Jiri playing the game once it is close.

## D18. One unsafe exception: the Lua instruction hook (2026-10-14)

`crates/sim/src/mission/hook.rs` uses about 15 lines of `unsafe` to install a raw Lua count hook that counts instructions and inspects the running function's registers for strings over 64 KiB, as the old sandbox did. mlua's safe hook cannot see registers and is several times slower per instruction. The rest of the workspace keeps `unsafe_code = "deny"`; any further exception needs a decision here.

## D19. Vision: knowledge per team, followed by comparison (2026-10-14)

Fog and remembered entities are kept once per team (allies share sight) and saved compactly (fog as runs, memories as snapshots of the entity as last seen). Sensors read the one exact `entity.position`; vision compares each sensor's position, height, radius and team with the previous pass every tick and updates only what changed, so any system that moves an entity is followed without notifying vision. Derived coverage is rebuilt on load and verified against the incremental data in tests.

## D20. Every player has a team (2026-10-14)

Teams are the only source of "ally": `canopy_sim::teams::Teams` resolves the match's slots so that every player has a team; a slot without a chosen team gets its own (the smallest number no other slot uses). Sight sharing, spells and auras that affect allies, AI and views all ask `Teams::relation` (own, ally, enemy, neutral) and never compare owners or special-case solo players. The UI need not show teams in free-for-all. Fixes the old quirk where team numbers and player indices shared one numbering.

## D21. Movement ported rule for rule, checked against the old game (2026-10-14)

Spatial model, navigation (grid A*, sectors, navmesh with the three.js 0.185 earcut ported exactly, walk-surface paths), traffic and orders follow the old code's algorithms, costs and tie-breaks (D15). During development, trajectories (positions and rotations every tick) were compared with the old game on scenarios covering crowds at chokepoints, deadlock yields, 400 units crossing a shipped map, a bridge, air units, patrol, follow and queued orders, and matched exactly; such comparisons are not kept as tests (D17). Derived data is new: compact body records in 4×4-cell buckets, per-cell blocker counts instead of owner stacks, edge and step caches, incremental mesh tiles; each is a pure function of state, so a restored match rebuilds it identically. The old envelope proof of clear sweeps is sound, so it now runs before every ground sweep, not only long ones. Units cooperate in traffic (waits-for negotiation, yielding, local claims, idle allies stepping aside) by team (D20), where the old code compared owners; route sharing and opposing-traffic search weighting stay per owner (one player's orders), and follow targets stay owned units. Game tick numbers start one lower than the old game's, which only shifts the phase of tick-hashed timing (idle strolls, separation stagger).

## D22. Combat ported rule for rule; engine ids in content are checked contracts (2026-10-14)

Targeting, swings, missiles and shells, damage, deaths, experience, camps and lookouts follow the old code's rules, numbers and tie-breaks: acquisition staggered by `tick % 8 == id % 8`, nearest by (distance, id), wind-up and recovery scaled by the attack cycle, damage summed per target and applied in id order, armour `1/(1 + k·armour)` rounded half up. During development, 25 scenarios (melee, missile and shell duels, armour, splash and slows, charges, flyers, focus fire, a 120-unit battle, assaults on buildings, camps with leash and loot, lookouts, attack, force, append, hold and attack-move orders, experience, levels, caps and fallen heroes) were run in both games and matched every tick: positions, health, swings, cooldowns, charges, slows, projectiles, corpses, loot and the random generator. As with D21 these comparisons are not kept as tests (D17).

- Damage is held in integer thousandths of a point (missile and shell damage are saved as `damageMilli`); mitigation is computed in `f64` and rounded half up as the old `Math.round`.
- Resolution asks exact sight after movement, so the world brings vision sensors up to date before step 7, and again after deaths so the dead no longer see, as the old live sensor index did.
- A dead hero stays in the entity table as **fallen** (no health, a fresh unit, on the cell it fell on) rather than being removed and re-inserted; revival (M2.5) brings the same entity back.
- **Engine-level content ids are named, documented constants checked when a world starts**, never literals in systems. The only one so far is `combat::rules::SPELL_DAMAGE = "spell"`: the damage type of untyped spell damage (mission `damage`, and later ability and item damage), which `rules.damageTypes` and `rules.damageMultipliers` must declare; content without it cannot start a match. The old `"normal"` fallback for units without a weapon was dead code (such a unit can target nothing) and is gone. New contracts go next to `SPELL_DAMAGE` and are checked in `Rules::new`.


## D23. Economy ported rule for rule; derived indexes; explicit starting workers (2026-10-14)

Jobs (deliver, construct, repair, harvest, plant with walk, wait, work, fall and return phases), the first-come harvest queue capped by `activeWorkers`, felling, depletion and regrowth, construction and its placement rules, training, rally points, pause, research, upgrades, revival, supply, wallets, accounting and defeat follow the old code's rules, numbers, messages and tie-breaks. During development, scripted matches on both shipped maps (starting gathering, mining, felling, a house and a forge built, training with a rally onto a tree, pause, research and its felling bonus, cancelled entries and sites with refunds, an upgrade refused, carriers and buildings removed with their goods and a building rebuilt, repairs, moves while carrying, defeat of three colonies and the outcome) were run in both games for up to 9,000 ticks and matched every tick: worker positions and cargo, jobs with phases and progress, wallets, accounting, building health, construction, production and research progress, the latest facts and every tree's felling state. Idle strolls and separation are tick-hashed, so these comparisons ran the old game with its tick shifted by one (D21). As with D21 and D22 they are not kept as tests (D17).

- **Derived indexes replace the old scans**: unit and building membership (followed lazily: ids are never reused, so creation shows as an advanced id counter and removal as a smaller live count), resources in 16-cell buckets, regrowing resources, and per-job aggregates (goods inbound per store, sites held by construct, repair and plant jobs) kept with the jobs and rebuilt when a save loads. `World::verify_economy` compares each with a cold rebuild. Static occupancy follows a depleted, regrown, placed, upgraded or removed blocker at once through `Spatial::sync_entity`; nothing rebuilds the whole forest.
- **Starting workers are explicit**: `spawn::placements` lists the starting units' placements, and the world gives their entities to start gathering. Nothing tests a placement-id prefix.
- **Map buildings are complete**, as in the old game, which never read `initialState.construction`; only the build command makes construction sites.
- **Supply messages name the player's own supply building**: the cheapest constructable building with `supplyProvided` in the player's race roster. The old messages said "Build a Mound" to every race.
- Every order change goes through `economy::interrupt` (via `orders::issue`), so a carrier finishes its delivery before a move, and workplaces lose their staff, as in the old game. Combat deaths release jobs, employment and paid tasks through `economy::work::release_references`; a fallen hero is revived in place.
- A decided skirmish stands still: the tick advances, nothing else runs, and commands are refused with "Match has ended".

## D24. Renderer decisions for M3 (2026-10-14)

- Every recommendation in [renderer §7](renderer.md#7-open-decisions) is accepted: one tonemapper plus a per-biome grade, MSAA 4×, one view-fitted PCF shadow map, no volumetrics or depth of field for now, the listed legacy shading paths cut, 4 blended terrain layers plus cliffs, normal-mapped rocks, authored effects converted by the cooker (their files unchanged), baked animation, live 3D portrait, presentation events from the simulation.
- **Maps up to 1024×1024**; larger maps are refused. This sets the terrain level-of-detail scheme and memory budget.
- **Interpolation delay accepted**: the picture trails the simulation by one 25 ms tick for smooth motion at any refresh rate.
- **No seasons, ever.** Biomes are the only environment configuration; a "winter forest" is simply another biome, not a season of one.
- **Lighting**: M3 matches the old game's current look inside the new, structurally clean pipeline; a separate graphics pass retunes it later.
- **Review**: each visual step comes with side-by-side captures (old game vs new renderer, same map, camera and units) for Jiri to judge.

## D25. Abilities, statuses and items ported rule for rule (2026-10-14)

Casting (targeting, eligibility, mana escrow, cooldowns, ranks, learning, autocast, cast orders and approach, prepare, channel and recover), every delivery (projectile, chain, line, charge, swarm), all sixteen operations with branches, queries, records and scales, persistent zones, toggles and auras, triggers and lifecycle reactions, summons and corpses, containment, split forms, forms, taunt, concealment and detection, spell vision, statuses (stacking, controls, damage policies, periodic effects, shields and mana shields) and items (inventory, pickup, drop and use, equipment, item auras, actives, rescue, on-hit procs, lifesteal and reflection, consumables and power-ups, regeneration accumulators) follow the old code's rules, numbers, messages and tie-breaks. During development, 49 scripted scenarios covering all of these (including a 32-unit brawl with heroes and casters autocasting, neutral camp casters, learning by level, weapon casts with autocast, death-raised summons and hero revival by ability) were run in both games and matched every tick: positions, health, mana and both regeneration accumulators, casts with phases, escrow and channels, cooldowns, ranks, autocast flags, weapon orders, statuses with timers, stacks and shields, item slots, runtimes, item statuses and bonuses, summons, containment, splits, deliveries, persistent instances, spell visions, corpses, missiles, every ability event and error, reaction queues and the random generator. As with D21–D23 these comparisons are not kept as tests (D17).

- **The ability and item libraries compile into the catalog** (`catalog.spells`, `catalog.items`) when content loads: abilities are `AbilityId` indices, statuses `StatusKey { ability, status }`, modifiers and control bits precomputed, forms resolved to definition indices. Nothing looks content up by string while a match runs.
- **Ability and item commands see the last completed tick**, like the old game, where commands ran between ticks: casts accepted with the command release on the same tick as there.
- **Ability events are presentation, not state**: about forty kinds (cast phases, impacts, statuses, summons, splits, containment, revival, combat modifiers, weapon orders), with viewers fixed when emitted; they are kept for 400 ticks (at most 1,024), drained by the client and never saved. Their presence never changes the simulation.
- **Delivery positions are integers in 1/128,000 cells**, exact for both milli-cell positions and the old game's 1/1024-cell snapping.
- **Budgets**: at most 128 lifecycle reactions (death, kill, interval, weapon release) run per tick from a queue of 512; combat reactions (hits, damage) are bounded by 2,048 queued events per tick; at most 512 deliveries and 512 persistent instances, 32 statuses per unit.
- **Spell damage that names no type uses `rules::SPELL_DAMAGE`** (D22); abilities and items add no other engine ids.
- **Old-game bugs fixed** (D14): a passive aura may carry triggers with any operations (the old content rule also scanned trigger operations, so an aura could not have a damage trigger); a line delivery needs no aim radius it never used (without one, the AI predicts a disc of the line's width at the aim).
- Revival at a building and by ability share one return: health, mana, casting state and both regeneration accumulators restart; a hero returning through an ability cannot be queued at a building, and supply counts it as returning.
- **Kept on purpose**: split members must be controllable, zero-supply non-hero units (the parent keeps its own supply and members are commanded by the player); only the first release operation is checked against the world when a cast is accepted, as later ones see the world the earlier ones changed; autocast and camp casting score only the release program, as before (the player AI that reuses it is M2.8).
- **Autocast considers only units that can matter**: those within the spell's range plus its widest area, delivery reach and the 24-cell threat radius, and the caster's own units anywhere. It skips the exact sight test for the rest, with identical choices.
- Taunted units do no work, haul nothing and enter no lookout; stunned workers neither start nor advance jobs and leave the harvest queue's waiting list, as in the old game.
- Removing an entity takes its unit body out of the spatial index at once (`Spatial::sync_entity`), as the old game did; units held by containment or a split form follow their host's whole cell.

## D26. Runtime asset pack and cooker (2026-10-14)

`canopy-cook` reads the mirrored data exactly as it is (D9) and writes one pack, `target/cooked/canopy.pack` (`canopy.pack` in the data folder of a package; `canopy_assets::find_pack` knows both). The game decodes no glTF, PNG or WAV.

- **Layout** (`canopy-assets`): a 64-byte header (magic, format version, digest of the cooked inputs), blobs, then a postcard index sorted by name. Little-endian, every blob and array 16-byte aligned. A blob is a 16-byte header, postcard metadata and plain arrays that metadata points into, so views are cast in place with `bytemuck` (no `unsafe`). `Pack::load` reads the file with one read; `Pack::open` reads the index and fetches entries on demand. Identical blobs are stored once. Entry names are the source paths (`assets/library/<id>/geometry.glb`, the path content already binds), with `#suffix` for parts (`#material0.base`, `#day`) and `@scenery` for the prototype table.
- **Models**: the authored transform (scale, pivot, forward), node hierarchy and soil offset (`groundContact: terrain` → −min y, as the old game) are folded into the vertices. Vertex: 16 bytes (unorm16 position in the model's box with the wind bend weight in w, octahedral snorm16 normal, unorm16 UV in the model's UV box); optional streams for vertex colour, leaf pivots (`_LEAF`) and skin (u8 joints, unorm8 weights summing to 255). One section per material with 16-bit section-local indices when they fit. A welded depth-only stream (positions and skin) holds every opaque shadow caster; alpha-tested sections are listed for the depth pass instead. Animated models get a joint palette in which rigidly animated nodes are joints too (felled trees, effect models), clips baked at 30 Hz as model-space 3×4 skinning matrices (Q13; frames `max(2, ⌈30·d⌉+1)` as the old bake), socket transforms per frame, the state table from `capabilities.animations` with event times normalised, and culling bounds over every frame and the wind sway. Materials are a model enum (unit, building, foliage, prop, effect) with numbers and flags.
- **Conventions are import-time inputs only**: team colour slots come from `capabilities.teamColor` (falling back to the `TC_TeamColor` name with a warning); `teamColorMask: "baseColorAlpha"` splits the base colour into opaque BC7 and a lossless R8 mask; the material extras the old renderer reads become fields, and those of cut paths (`referenceEnvironment`, `sourceShader`, `resinShimmer`…; Q5, Q6) are dropped; `foliageWind` node extras give the sway; nodes named `socket*` are sockets. The old game ignored `capabilities.wind` and the published `team_mask.png`; the cooker follows what it actually rendered and carries `capabilities.wind` alongside for the renderer.
- **Textures**: BC7, sRGB for colour roles (albedo, emissive, icons, interface, effect images, albedo tiles) and unorm otherwise, all mips, filtered in linear light: premultiplied for translucency, coverage-preserving for alpha-tested foliage, renormalised for normal maps, alpha kept independent where it is data (terrain tiles). Sizes round to whole 4×4 blocks (Catmull-Rom; the source size is kept for layout). Team masks stay uncompressed R8 (lossless). Colour grades become RGBA8 volume textures (BC volumes are not in the WebGPU baseline). No uncompressed copies are shipped: a device without `texture-compression-bc` (D2; Apple Silicon and DX12 have it) decodes BC7 at load (`Texture::decode_level`).
- **Sounds** stay 16-bit PCM: the two effect sounds are 82 KB; decoding Vorbis or Opus at load would cost more than it saves. Revisit when music arrives (M4).
- **What is cooked** is decided from the data's declarations: every glb; images of records without geometry; of model records only the images a render binding shows (the rest are copies of textures the glb embeds); not the channel images of terrain materials whose catalogue entry declares packed tiles (editor previews), but the gzip tiles themselves; other `.bin` as data; colour-grade JSON; map previews. Recipes and profiles stay in the catalogue JSON the game reads.
- **BC7 encoder: Intel's ISPC Texture Compressor through `intel_tex_2`** (prebuilt kernels for macOS arm64 and Windows x64), "fast" settings for colour and data, "basic" for normal maps. Measured on an M4 Max, 16 threads: "fast" is within 0.1–0.5 dB of "basic" on colour at about half the time; normal maps lose up to 1.5 dB with it. The pure-Rust port of the same kernels (`block_compression`, CPU path) gives the same PSNR (within 0.02 dB) and is bit-identical across platforms, but is 2–3× slower (a cold cook of 162 s against 31 s). Rejected: GPU compute encoders (results differ by GPU), `texpresso` (no BC7), bc7enc-rdo and Compressonator (C++ builds for little gain). Kept from `block_compression`: the BC7 decoder for the fallback and tests. The prebuilt kernels lack a macOS platform load command, so the cook binaries allow `linker_messages`.
- **Incremental, parallel, deterministic**: source files are hashed with BLAKE3 behind a size/mtime stamp cache; a job's hash covers the cooker and format versions, its parameters and its sources; textures are cached by image bytes and parameters, so models sharing an image encode it once; unreferenced cache files are removed. Jobs and BC7 strips run on every core; output order is fixed, maths uses `libm`, so the same inputs give a byte-identical pack. On Apple Silicon the ISPC kernel is a single NEON build; on x86 it dispatches by CPU instruction set, so Windows cooks may differ between machines (cache keys are per machine anyway).
- **Numbers** (M4 Max, shipped data, 441 MiB of cooked sources): cold cook 31 s, no-op 0.03 s, one model or icon changed 0.3–0.8 s (mostly relinking); pack 681 MiB (textures 625, models 56); loading the whole pack 89 ms (one read, warm file cache); validating every entry's metadata and views 0.4 ms.
- **Packaging** ships the pack and the JSON the simulation reads (`content/`, `assets/manifest.json`, the authoring indexes, maps) instead of `assets/library`. CI has no LFS art, so the package step cooks with `--allow-lfs-pointers` and ships a pack without it.
- **Not yet**: `Content::load` still checks that every published output exists on disk, so a packaged game cannot load content until that check consults the pack (game integration step). Pack supercompression (zstd over BC7), half-precision or sparser clip storage and the v2 effect conversion (Q11) wait for measurements and the effects step.

## D27. AI ported rule for rule from the player's knowledge (2026-10-14)

AI players (`canopy_sim::ai`) follow the old `PlayerAI` layer by layer: briefing and geography, a per-decision frame, known blockers and navigation, ability learning and casting, heroes and items, strategy, economy, reactions, operations and order continuity, with the old timings, stagger, sequence numbers (above 1,000,000), limits (four commands, one spending command and one command per actor per decision, at most 32 pending) and thresholds. During development, AI-versus-AI matches on both shipped maps were run in both games with the full content (the old game's tick shifted by one as in D21, and the fixes below switched off) and every AI command (tick, player, sequence number, action) matched: Echo Isles with two AIs through the old game's outcome at tick 34,112 (2,020 commands, 55 casts, the same winner), Turtle Rock with four AIs for 12,000 ticks (831 commands, 37 casts). Before abilities and items were merged, the same comparison with them neutralised in content matched through Echo Isles' outcome at tick 27,673 (1,503 commands). As with D21–D25 these comparisons are not kept as tests (D17).

- **The M2 finish line** (`tests/ai_match.rs`): AI-versus-AI matches end on their own on both shipped maps (with the fixes below: Echo Isles duel at tick 67,522, Turtle Rock duel at 75,786, Turtle Rock four-player at 89,025, 28 to 37 game minutes), with identical fingerprints every tick and identical final states when saved and restored half way. A 1,200-tick duel runs in CI; the full matches are ignored tests (about two minutes in release).
- **Knowledge, not views.** A decision reads what its player's view lists (own entities, others in sight through the team's fog, remembered structures, known scenery) straight from the state through `Sight`, without building or cloning a `View`; private state is read only for own entities, and enemies' mana counts as unknown.
- **Known navigation reuses the engine.** Each AI keeps reference-counted cells of known buildings and resources, and runs the engine's sweeps, clearance proofs, sector graph, grid search and navigation mesh over that known walkability. All of it is derived: rebuilt from knowledge on load, and its caches answer as a cold rebuild.
- **Placement applies the engine's foundation rules to knowledge**, not `World::can_build`, which would consult blockers and units the player has not seen. A site the simulation refuses is avoided for 1,200 ticks, as before.
- **Memory is saved state** (`State::ai`, D16): a restore checks the briefing fingerprint and that every pending AI command is in the saved queue.
- **Decisions run on this simulation's tick numbers** (one lower than the old game's, D21); the per-AI stagger is unchanged.
- **Abilities use the ability runtime's scorer** (`abilities::ai`, D25) with the old player rules: learning by newly unlocked rank, then breadth, then the race's `skillPreference`; one cast per caster per decision, the first AI binding with a useful aim; tactical intents take the first sampled destination.
- **Fixed (D14)**; players will notice the first five:
  1. The old observation boundary dropped appearance scale, so the AI saw every tree at full size: forests looked closed, units standing in them counted as obstructed, and their retreat and assembly points collapsed onto their own position.
  2. The boundary also dropped a deposit's workforce, so the recommended number of workers per deposit was never respected; it is for deposits in sight.
  3. The AI sent workers to gather remembered resources out of sight, which the simulation refuses; each refusal cost the economy pass and was retried. Gather targets must be in sight.
  4. Archer spacing compared the weapon's remaining cooldown with the match tick, so it never happened after the first seconds; ranged units now step back after a shot when a melee enemy is close.
  5. Spell scoring for the player AI follows the whole release program as it would run: every operation chooses its recipients from the units as the earlier operations left them (converted, killed, moved). The old scorer did so only for operations with a query; the others chose from the units as they were when the cast began. Enemies' statuses (public) now count in scoring; the old boundary dropped them, so the AI re-applied statuses enemies already had and ignored their immunities. Autocast and camp casting keep the old rule (D25).
  6. Sorts without a total order now break ties by id (then coordinates); an empty army composition no longer yields a NaN army target.

## D28. AI gameplay fixes kept (2026-10-15, decided while Jiri was away — review)

The five AI fixes from the M2.8 port (D27) stay: ranged units step back after a shot when melee is close, trees seen at their real scale, recommended workers per deposit respected, no gathering orders for unseen resources, spells judged by their whole program. They make the AI play as the old code intended.

From here until Jiri is back, decisions he would normally make are taken by the lead with the best available judgement and recorded here marked "review".

## D29. Audio on kira; the old effect-sound model, voice budgets and buses (2026-10-15, decided while Jiri was away — review)

`canopy-audio` ([audio](audio.md)) plays effect sound layers as the old game did and adds what the old game lacked.

- **kira 0.12 on cpal** (macOS CoreAudio, Windows WASAPI) rather than cpal with our own mixer: its audio thread does not allocate (fixed arenas, lock-free queues; our `no_alloc` test checks the renderer), it handles device loss, resampling, playback rate, tweens and tracks, can stream compressed music later, and its mock backend runs the whole mixer in CI without a device. Gain and pan are computed on the main thread with the old model, so kira's spatial tracks are unused. Without a device the game runs silent.
- **The old model exactly**: listener at the camera's ground focus, quadratic falloff from `referenceDistance` to silence at `maxDistance`, pan `lateral / max(ref, d)` with the old equal-power law (mono clips at −3 dB and the pan passed as `sin(p·π/2)` reproduce Web Audio's gains), tick-sampled timelines (offset `age × pitch`, rate `pitch × speed`, re-sync beyond 0.12 s), silence while paused. The cue lifecycle follows the old effect player: delays, durations, delivery durations, looping effects, status lifetimes, 5-second aura pulses, `follow`, cancellation, returns.
- **Voice limiting** (felt): categories Effect, World, Interface and Music with their own budgets (24, 16, 8, 2 voices); within a category the most audible requests win (the old game took the first 24), at most 6 copies of one effect sound and 4 of one world sound, a 25% hold for playing voices; world and interface one-shots of the same sound within 40/30 ms merge; inaudible and muted sounds take no voice. Losers stay virtual and keep their timeline.
- **Buses and defaults** (felt): master 1.0, effects 0.65 (the old "Spell effect volume" and default), interface 0.7, music 0.5; linear gains multiplied together as before; muted while the window is hidden (setting, on by default; the old game suspended audio in a hidden tab).
- **Presentation fixes** (D14): projectile sounds start once per cast (the old renderer could stack copies), status cues are keyed by the unit holding the status (a caster-anchored status layer no longer restarts every frame); sound layers ignore model sockets.
- **Music**: playlists with equal-power crossfades and shuffle are ready; tracks are PCM clips until music exists, when the pack format gets compressed audio and streaming (D26's "revisit when music arrives").
- `canopy-audio` depends on `canopy-sim` only for `observe(&View)`, the adapter from views to effect triggers; the effect-sound core takes plain triggers and sightings.

## D30. Biome look and presentation settings are data in `config/` (2026-10-15)

The old game defines biome lighting, atmosphere, grading, ground layers and surroundings in code (`src/content/biomes.ts`, `src/shared/environment/*`, `sky.ts`). They now live in this repository's own top-level `config/` folder, owned here and outside `content/`, `assets/` and `art/` (which `just sync-data` mirrors and would overwrite): `config/lighting.json` (day and night palettes per daylight profile, dawn and dusk phases, the ground probe and environment irradiance, shadow fitting), `config/biomes/<biome id>.json` (one per id a map may name), `config/players.json` (player colours) and `config/glow.json` (deposit glow). `canopy-render` reads and validates them strictly (unknown fields, the old editor's ranges, references to daylight profiles); `canopy-scene` resolves asset references against content; packages ship `config/` in their data folder. Values reproduce today's look: resolved numbers were checked against the old renderer (sun 3.2 from (−0.406, 0.707, −0.579) at noon in the vibrant forest, ambient 0.82, hemisphere 0.65/0.84/1.14 over 0.18) and the frames agree within a few levels of 255 (renderer §10). Derived constants are stored as data with their source: the ground probe is the old reflection cube's last mip, the environment irradiance the SH9 projection of the old procedural forest environment as it was actually sampled (upside down). Settings for effects not rendered yet (bloom, contact shadows, volumetric atmosphere) are carried so the biome files are complete. Why: biomes are content in all but location; Jiri tunes looks without code, and a later live-tuning UI writes the same files.

## D31. Renderer core for M3 (2026-10-15)

- **Crates**: `canopy-render` (device, frame graph, passes, shaders, camera maths, config types) and `canopy-scene` (the only bridge from maps and the simulation to the renderer's plain `World`). The game owns input and the window; `canopy shot` renders offscreen.
- **WebGPU baseline (D2)**: default limits; only WebGPU features, optional with fallbacks: `texture-compression-bc` (D26) and `timestamp-query` (pass timings). `indirect-first-instance` is not used (visible lists are reached through dynamic storage offsets), nor multi-draw-indirect, push constants or timestamps inside passes. MSAA attachments use the WebGPU `TRANSIENT_ATTACHMENT` usage. No exceptions are needed.
- **Today's look first (D24)**: one lighting function with a *ground* ambient model (the old terrain path) and a *standard* one (three.js physical as the old units, buildings and painted foliage used it); the one tone mapper is the old highlight shoulder, bypassed (clip) for every current biome as the old outdoor frames were; the biome grade is one baked 32³ volume. The canopy shade multiplies everything under it, as the old composite did. A retune is a separate, agreed step.
- **Shadows**: one 2048² map fitted to the view's ground slice (−6…+12 around the focus, padded, size in 4-unit steps), anchored at the world origin and snapped to texels; 8-tap rotated Vogel PCF with the biome's softness as radius (the old VSM blur radius). Casters shorter than 0.75 m are skipped, as before.
- **Terrain**: 32-cell chunks, 4 geomipmap levels chosen by projected height error ≤ 1 px, vertex-pulled heights, stitched edges; at most 4 blended layers per one-unit cell (Q7), cells aligned to the texture grid; layer lists, masks and atlas codes built once at load.
- **Scenery and buildings**: one instance buffer culled on the GPU for camera and sun every frame; one indirect draw per model section; alpha-to-coverage for alpha-tested foliage under MSAA; the old trunk sway and leaf flutter in both passes. Draw calls depend on the models present (29 on the shipped maps), not on instance counts.
- **Positions follow the old renderer**: decorative stamps stand at the cell centre `(x + 0.5, y + 0.5)`, standing trees at their resource cell, buildings at their footprint centre; scale is render asset × appearance × definition for settlement models and appearance alone for trees.

## D32. Multiplayer client `canopy-net` (2026-10-15, decided while Jiri was away — review)

`canopy-net` is the client of the old match server (D10), checked against it rather than a recording: the integration tests run `server/index.ts` from the old repository locally and play matches with Rust clients driving `canopy_sim::World`; a TypeScript client (the old repository's own `lobby.ts` and `ws.ts`) shares a lobby with a Rust one; the outbox and mailbox replay long random traces through the old `Lockstep` and `Room` and must send byte-identical messages. These tests skip themselves when the old repository, its `node_modules` or node is missing (CI). Read-only checks against the deployed server are ignored tests.

- **Wire**: client messages serialize to exactly the old client's JSON, key order included. Server messages are read leniently (unknown fields ignored), because the server spreads content records into room views (`heroes.offset`). Action key order follows `canopy_sim::Action`; the old client's call sites each had their own and nothing downstream reads it.
- **Threading**: one `canopy-net` thread runs a single-threaded tokio runtime with reqwest (lobby HTTP) and tokio-tungstenite (match socket) over rustls. The async runtime stays inside the crate: a socket task must wake both for server messages and for player commands, which a select over the socket and a channel does without polling timeouts or splitting a TLS stream across threads. The game gets synchronous handles: `Session` lives on the simulation thread and never blocks; `Commands` hands commands in from any thread, and the socket task confirms them at once, as the old client's `send` → `pulseConfirm` did. Lobby calls return `Pending` replies to poll.
- **TLS**: rustls with the `ring` provider and `rustls-platform-verifier`: the system trust store and settings on macOS and Windows, checked live against the deployed server's IP-address certificate. No certificate checks are ever disabled.
- **Server address**: the deployed `18.134.138.1` over HTTPS/WSS; `CANOPY_MATCH_SERVER`, then a game setting, override it. Plaintext `http://`/`ws://` is accepted only for loopback hosts (a local copy of the old server).
- **Beats and ticks**: server beat `T` (from 1) is the step starting at `World::tick() == T - 1` (the simulation counts one lower, D21), so its commands are queued for tick `T - 1` with their index in the slot as sequence number. The `hash` for beat `T` is `World::fingerprint()` after that step, every `checksumEvery` (8) beats, as an unsigned 32-bit number.
- **`ready` identity**: `abi` `canopy-sim-1`, `build` `canopy-<version>` (the game may pass a sharper build id) and a SHA-256 over the content the match runs on (`ContentIdentity::digest`; the game chooses the files). A Rust and an old client in one room are therefore refused with `CONTENT_MISMATCH` at the start instead of desyncing, since their simulations cannot agree.
- **Committed actions nobody can read** (or that fail `Action::problem`) are skipped by every Rust peer identically and reported; the others keep their sequence numbers.
- **Single-player** runs through the in-process mailbox with an input delay of one beat (the old `MemoryChannel`), so local and networked play feed the world the same way.
- **The end of a match**: `Session::report_outcome` sends `ended`, which ends the room for everyone. The old client never sent it, so finished rooms stayed listed as playing forever (they are visible on the deployed server). The game should send it once the outcome is decided. (review)
- **Not supported; the session stops with a reason**: the host's restart and save load (the old client handled neither; a restart also carries in-flight confirmations into the new mailbox), and joining a running match as a spectator (the server sends no history). There is no automatic reconnect, as in the old client: the server cannot replay the commits a dropped seat missed. Multiplayer has no pause (the server has none; the old client ignored pause when networked).

## D33. UI toolkit `canopy-ui` (2026-10-15, decided while Jiri was away — review)

`canopy-ui` draws the HUD and menus as [docs/ui.md](ui.md) describes; the old game's DOM HUD and stylesheets are the reference.

- **A retained tree built from data, updated immediate-style**: screens and widget templates are JSON layout documents in `config/ui/layouts/` styled by `config/ui/theme.json`, written as CSS properties (taffy parses the layout values), so the old stylesheets port almost literally. The game pushes its models into named nodes each frame; setters invalidate only what changed; layout and shaping re-run only where text sized a box. Both files hot-reload in debug builds and keep the game's values. Rejected: immediate mode (layouts would be code, taffy and shaping would rerun every frame) and a hand-written widget API (no designer iteration).
- **One quad pass**: every primitive (rounded boxes, borders, shadows, gradients, sweeps, nine-slices, images, glyphs) is a 64-byte instance of one pipeline; batches split only on image texture or scissor. The reference wgpu pass lives in the crate (feature `wgpu`); the renderer may embed it.
- **Compositing in sRGB space**, as the browser did, so the old colours, gradients and translucency match; the renderer draws the UI into a non-sRGB view of the target (or the pass linearises for sRGB targets). Textures may be bound through sRGB views (`ImageDesc::srgb_view`). (review: visible)
- **Fonts**: Outfit (the old HUD font, OFL 1.1) is bundled from the old game's npm package, converted from WOFF2. Georgia and the system UI font, which the old game took from the operating system, are again taken from the operating system (both ship with macOS and Windows; neither may be redistributed), with Outfit as the fallback. Recommended follow-up: bundle Gelasio (OFL, metric-compatible with Georgia), which needs a font download that was not made unattended. (review: visible)
- **Tooltips show at once** (`delay-ms: 0`), as in the old game; the delay and the warm switching window are theme values. (review: felt)
- Boxes default to `position: relative` (absolute children are placed in their parent, as every old HUD rule assumed).
- Requested font weights snap to a static family's faces as CSS matching does; cosmic-text alone matches exact weights only.
- Tests use their own theme and layouts; text tests fall back to system fonts when the bundled font is a Git LFS pointer (CI). The gallery render test skips without a GPU adapter.
- `Ui` is not `Send` (taffy styles hold calc pointers): it lives on the window thread.

## D34. Water, post effects, surroundings and render scale for M3 (2026-10-15, decided while Jiri was away — review)

[Renderer §4.6 and §9](renderer.md) describe the result; [captures](captures/README.md) compare it with the old game.

- **Water is redesigned around the old shading model, without a scene copy.** The old water copied the frame's colour and depth, marched 64-tap screen-space reflections and refracted the bed. Here it is drawn inside the MSAA forward pass in two draws over the same fragments: one multiplies the bed by the hue of the water column's absorption, the other blends the surface with premultiplied alpha carrying the rest of the bed's dimming. Together they reproduce the old per-channel transmittance exactly (echo-isles shallows within 1–2 of 255). Every other old term is kept (body colour, caustics, swell bands, the old woodland reflection cube, glints, shore/crest/flow foam, cloud and canopy shade, unit wakes). Dropped on purpose: refraction (about 2 px at RTS zoom) and screen-space reflections (2–4 % of the colour at the 56° pitch). Dual-source blending would make it one draw but WebGPU allows it only with a single colour target, and the forward pass has two (below). (review: the look)
- **Ripples are ported one-to-one** (1.7 m spacing, 3 per body and 256 per frame, 1,536 rings, 2.8 s, 768² RGBA16F over 160 m, Gaussian crest). The live world feeds `Renderer::ripples_mut().update(movers, field, seconds, focus)` every frame with plain `Mover`s (id, position, walking surface, elevation); bridge decks come through the `WaterField::walk` surface id.
- **Linear depth is a second forward colour target** (RG16F: the view depth rounded to 11 significant bits plus the remainder, exact through the MSAA resolve for interior pixels; WebGPU resolves neither depth nor R32F). It costs no memory traffic beyond one resolved RG16F image, where storing the multisampled depth would cost about 66 MB per 1080p frame. **Contract for every forward pipeline** (units and effects included): declare `targets::forward_targets(blend, writes_depth)` and return `scene_out(colour, world)` from opaque fragment shaders (`frame.wgsl`); transparent ones pass `false`. The water writes its surface, so post effects stop at the water like the old ones.
- **Post effects run only where the biome uses them and the quality allows**: the frame graph is rebuilt from `FrameFeatures` (water, contact, bloom, haze) when the world, biome or settings change; a pass that does not run does not exist. Contact shading, bloom and the volumetric haze follow the old `BeautyPass` and `AtmospherePass` with their budgets (effect buffers at most ½ scene and ~180k pixels; haze low/medium/high = 0.33/0.5/0.66 scale, 16/24/40 steps, 180k/360k/900k pixels; medium by default as in the old game). The old composite clipped every surface at the plane `waterLevel − 0.03` and committed-cell maps leave `waterLevel` at 0, so the old game had no contact shading on ground below y ≈ 0.05; that quirk is not kept (D14) — ground around the shipped maps' shores now gets contact shade. (review)
- **Render scale** is a quality setting (0.5–1; the scene renders with MSAA at the scaled size and the final pass upsamples with a light unsharp mask, strength 0.25). Default 1. **Recommendation for the base M1**: 1.0 at 1080p, 0.75 on Retina panels (2560×1600 → 1920×1200 internal), from the measurements in renderer §9 scaled by the GPUs' throughput. (review)
- **Surroundings** follow the old generator exactly (seeded LCG, anchor rings, forks, leaf grid) so the same biome and map size place the same forest; the data moved to `config/biomes/*.json` `surroundings.forest` (scenery ids, rings, leaf colours, bark texture) and the shared water textures to `config/water.json`. As before, the camera's map fit keeps the forest out of every play and spectator view; it shows only in free views.
- **Pass timings on Apple GPUs are coarse**: timestamps at pass boundaries attribute work to neighbouring passes (the final pass always reads 0 ms). `canopy shot` therefore also prints the median submit-to-idle time of the measured frames; budgets use both.
- **WebGPU baseline (D2)**: nothing new is requested; no exception needed.

## D35. The live world: simulation thread, presentation, interpolation and live models (2026-10-15, decided while Jiri was away — review)

M3.3 makes matches watchable: `just play --spectate <map> [--players N]` runs computer players on the map's starts; `canopy shot --tick N` simulates to a tick first (renderer §9, §10).

- **Simulation thread** (`game/src/sim.rs`): the world steps on its own thread through `canopy_net::Session::local` (observer seat), so multiplayer later uses the same path. Tick `n` belongs to simulation time `epoch + 25 ms · n`; the thread computes it **one tick early** so a tick's cost (up to 25 ms) never shows as a hitch, and never earlier, so the match never runs faster than real time. Behind by more than 8 ticks, it catches up at full speed for those 8 and moves the schedule for the rest (the match slows down instead of skipping or bursting; results never depend on timing). A player's commands will therefore reach the screen one tick (25 ms) later than with no lead. (review: felt)
- **Hand-off**: the newest 4 presented ticks sit in a ring behind a mutex the simulation holds only to push a pointer; the render thread checks an atomic tick counter and `try_lock`s, keeping what it has when the lock is busy. It never waits for the simulation.
- **Presentation runs on the simulation thread, once per tick** (`canopy_scene::live`): the observer view becomes posed models (transform, owner colour, opacity, up to three clip poses) with the old game's rules; animation state choice and clip clocks advance per tick (D24's tick-addressable animation), so the same tick presents identically (shots are deterministic) and the render thread only interpolates. It costs about 0.2 ms a tick in a duel and 1.3 ms with 500 fighting units (M4 Max).
- **Interpolation** (Q15): the picture shows simulation time minus one tick, between the two presentations around it: positions and scales linearly, rotations along the short arc, poses clip by clip (looping clips wrap, restarted one-shots take the new time). New models, model changes and moves over 3 cells in a tick do not blend. No extrapolation: a late tick holds the newest picture.
- **Animation as in the old game** (`animation.rs`): clips play at 1.5×; aliases sharing a clip (run, charge) keep their phase; one-shots return to idle (not death); linear cross-fades from the current weight, at most the current and two fading clips; attack wind-up maps onto `[0, contact]` and recovery onto `[contact, 1]` from the swing's ticks; work strokes follow the authoritative cycle and face the work; cast phases follow the old `castAnimation`; a hit plays the hit reaction when standing and tilts the body for 0.22 s. The engine's state names (`idle`, `walk`, `run`, `charge`, `attack`, `hit`, `cast`, `death`, `carry*`, and the content's work animations) and the cargo node `socket_back` are the old renderer's contract with the asset pipeline, not content ids.
- **Static and live split**: map stamps and every tree stay in the static scene (D31); a tree leaves it (a 16-byte flag write) once struck or gone and the live scene plays its hit, fall and decay clips at 1× from the felling ticks. Everything else is live: units, buildings (depletion stages, construction scaffolds rising until the race's reveal point, model swaps on upgrade), items on the ground, carried goods at the back socket, corpses, missiles and shells.
- **Live models on the GPU** (`canopy_render::actors`): CPU culling against the camera and the sun (cheaper than a compute pass at these counts, and it keeps the draw list), instances sorted by model with camera-visible ones first, one skinning job each; a compute pass blends model-space 3×4 matrices (Q13) for up to three poses between two baked frames into per-instance palettes; one instanced draw per model section reads a contiguous range (direct draws with a first instance, which the WebGPU baseline allows). Rigid models skin with one identity joint, so one pipeline serves everything. Statics and live models share one material module (`shaders/lib/material.wgsl`, `material.rs`). No WebGPU exceptions.
- **Deaths follow the old renderer**: a unit that dies in sight plays its death clip for two seconds where it fell (a flyer drops to its floor at `15 t²`), then vanishes; fallen heroes are hidden until revived. The simulation's raisable corpses are not drawn, as before.
- **The view lacks one fact**: whether a unit is held inside another entity (`contained`, `release`). The presenter reads it from the world on the simulation thread (observer only, so nothing leaks); the view should carry it (follow-up for `canopy-sim`).
- **Projectiles** use the shooter's weapon effect layers (model, size, rotation, offset, arc) from content; the layer colour tint is not applied (every shipped weapon layer is white).
- **Shot and stress tools**: `--tick N` (deterministic, presents every tick), `--camera battle[,zoom]` (centre of the densest group of swinging units), `--crowd N` (eight players with N animated soldiers each around the middle of the starts, each with a small building so skirmish rules keep them in), `--colors i,j,…` (player colour per slot, for colour reviews).
- **Dev builds optimise `canopy-sim` and `canopy-scene`** (opt-level 2, like the cooker): unoptimised, a mid-game tick costs over 25 ms and `just play --spectate` could not keep time.
- **Measured** (M4 Max, 1080p, after the water and post effects; base M1 still to measure): the 8 × 50 crowd view (491 animated units visible, 554 shadow casters, 26,700 joints) takes 3.2 ms from submit to idle against 2.0 ms for the same view without the crowd, 0.4 ms of CPU to record and 0.013 ms to interpolate; the palette pass costs 0.01 ms. In a window (Retina, about 3200×1800) a 450-unit battle ran at 245 fps uncapped before the post effects. Scaled to the base M1 (about 7× less GPU), 400+ units in view would cost about 8 ms on their own at 1080p, so the worst case needs a cheaper unit path (fewer shadow casters, lower-detail shadow meshes or level of detail) or render scale below 1 to stay under 16.7 ms; ordinary fights of 50–150 units fit. (review: performance against quality) The simulation thread: 0.3–0.6 ms a tick in a duel, 8–16 ms with 400 fighting units (spikes to 30–50 ms as the armies meet, which the one-tick lead hides up to 25 ms), the simulation's own cost (M2).

## D37. Simulation performance work keeps results bit-identical (2026-10-15)

Speed-ups in `canopy-sim` must not change a single simulated value: every tick fingerprint and the final saved state stay identical, checked with the digest of `just bench-sim` (crowd battles and AI matches) before and after, besides the determinism tests. Concretely: caches are pure functions of the state they read and are forgotten whenever that state can change (autocast remembers sight answers and unit snapshots only until the next cast); "is there any" queries may test candidates in any order and skip ones that provably cannot answer (the sight index skips sensors not shared with the asking team; attack approach first tries the bodies touching the actor); "the first in order" searches keep their order (attack approach pops a heap and sorts only the candidates that pass the pure tests). A faster rule that would change tie-breaks or outcomes is a gameplay change and goes to Jiri (D14).

- The measured crowd battle (`canopy shot --crowd N`) lives in `canopy_sim::crowd`, so the shot tool and the benchmark run the same scenario. `World::step` marks its steps with `tick: …` spans for Tracy and the benchmark.
- Numbers and the remaining hot spots are in [simulation § Performance](simulation.md#performance).

  - Campaign cards come from `rules.campaigns` (the old screen hard-coded three with two locked); the crest is `asset.interface.campaign.<race>` as the old screen used. Missions unlock in order as the previous one is won (progress in `campaign.json` in the user folder); the old list had no locks. No mission maps are mirrored yet, so the mission list shows its empty state, as the old game does.
  - Settings is a tabbed dialog (Graphics, Audio, Interface, Keyboard, Multiplayer) in the old dialog's style, because it holds far more than the old single column.
  - The match result keeps the old dialog and adds what the simulation knows: duration, every player's result, live units and buildings, and the goods gathered, spent and lost (accounting is global, not per player). "Keep watching" hides it; leaving goes back to the match's origin, a won mission offers the next chapter.
  - Loading shows the old plain panel for skirmish and multiplayer and the mission version (art, chapter, title, briefing, tips, pill bar) for missions and the boot screen.
- **Settings file**: `settings.json` in the user folder (D6), versioned, every field optional (missing fields take defaults; an unreadable file is moved to `settings.json.bad`), written atomically when the dialog closes and on exit, applied as values change. Graphics: render scale (D34), a **resolution cap** (the old "Game resolution": the scene renders at most that size, the interface stays native; implemented through the render scale), shadows, contact shading, bloom, haze, vsync, windowed or **borderless fullscreen**. MSAA stays fixed at 4× (D24) and is not a setting. Audio: master and the three buses, mute in background (D29). Interface: player name, HUD size (applied to the HUD dock), always-show health bars and tooltips (applied to the play HUD and its world UI, D39). Multiplayer: the server address (`CANOPY_MATCH_SERVER` still wins).
- **Shortcuts**: the engine's shortcuts with the old defaults (`settings/keys.rs`), chords named like `KeyboardEvent.code` and stored as overrides only; a key taken by another entry is refused ("Already used by …"), Enter is reserved for chat, only the old allowed keys bind and only health holds may be bare Alt; shared keys from hand-edited files are flagged. Content-derived command shortcuts stay with the content (the play module's command card) and are matched after the engine's (D39).
- **Save format** (D16): each save is a readable `saves/<id>.json` header (name, time, mode, map name, player, tick, and the identity: map id, SHA-256 of the `.utcmap` and of the content files) and `saves/<id>.save.gz`, gzip over JSON of `World::save()` plus the camera. JSON because the simulation state skips absent optional fields, which binary serde formats cannot read back; gzip makes a mid-game save a few hundred kilobytes. A save loads only on the same content and map revision. Unlimited saves as in the old game; one `autosave` slot is written when the window closes during a local match. A loaded match continues through `Session::local_from`, a new `canopy-net` entry point that starts the in-process mailbox at the saved beat (the plain local session would have refused confirmations past 4,096 beats).
- **Multiplayer in the screens**: the discovery list polls `/api/health` and `/api/rooms` (every 5 s), creating and joining go through `Net`, the room's session is polled while the lobby shows (seats, races and heroes from the server's content, measured round trips, input buffer) and moves into the loader when the server starts the match. The world is built from the frozen config; `ready` reports `canopy-<version>` and a SHA-256 over the content files and the map file. In the match the simulation thread polls the session (chat, desync, stop, close, end → overlays), "Waiting for players…" shows after 1.5 s without the next beat, and every peer reports the outcome once decided (D32; the server keeps the first). A seat whose session receives `ended` before it simulated the deciding beat shows the result from the server's outcome.
- **Surrender** has no simulation action: single-player shows a defeat and holds the match; in multiplayer it shows the defeat and leaving closes the seat (the others play on, as the old Leave).
- `canopy-ui` gained two paint-level setters, `set_opacity` (fades) and `set_shift` (animation offsets), which do not re-run flex layout.

## D39. One game: the screens run the in-match play (2026-10-15, decided while Jiri was away — review)

The screens (D38) and the in-match play (D36) were built in parallel and are now one game: the flow owns the app, and a match started for any seat runs the real `play::run::InMatch` inside `screens/in_match.rs` (the player's HUD, input, placement and fog through the seat's view; the observer HUD for spectators). `--map` and `--spectate` jump through the flow straight into a match; `--map` now plays (it used to show a paused observer view).

- **One UI, one pass, one texture table.** The screens' `Ui` also holds the HUD documents; `InMatch` no longer owns a `Ui`. Everything draws through the renderer's `ui` pass (`canopy_render::ui::UiLayer`): inside the frame graph in a match, alone over a cleared target in the menus (`UiLayer::encode_alone`). Screen images are bound there from a high id range (2²⁰ up), so render targets (`plug_render_target`, below 1024) and the renderer's own pack images (1024 up) keep their ids. The debug overlay draws after the UI (on top of menus too). Pack images draw with straight alpha everywhere: the cooker stores them un-premultiplied (D26), and the renderer's UI layer had marked translucent ones premultiplied (dark fringes).
- **Input order**: the UI sees each window event first, then the match with whether the UI took it. While an overlay (game menu, settings, result) is open the match only follows releases and focus; the menu opening releases held keys and drags. The HUD's UI actions (paths under `hud/`) go to the match, the rest to the screens.
- **Shortcuts come from the rebindable catalogue** (`settings/keys.rs`): camera pans and zoom, the game menu, cancel, heroes, idle worker, subgroups, next hall, centre selection, alerts, control groups (recall, assign, add), placement rotation, inventory slots, health bar holds, the debug overlay and hiding the HUD are matched from the player's bindings (`play/keys.rs`, `Keymap`); a key no engine shortcut takes goes on to the content's command hotkeys. Cmd stands in for Ctrl when nothing is bound with Cmd (D36). Escape still cancels a mode, goes Back or opens the game menu even if `interface.cancel` is rebound, so the menu can never be lost (review: felt). Spectators' Q/E turn, B (largest fight) and F9 stay fixed (not in the catalogue).
- **Settings in the match**: "always show health bars" makes `HealthBars::All` the default (holds still narrow it); tooltips off hides tooltips while the HUD has the input (menus keep theirs); HUD size scales the dock as before; render quality applies to the shared renderer; one `Audio` (the screens') plays the match's effect sounds and is updated by the match while one runs.
- **One chat**: the play HUD's chat. In multiplayer a line goes to the match server and shows when the server echoes it (it delivers chat to everyone, the sender included), with the sender's colour; single player shows it at once. The screens' separate overlay chat was removed. (review: visible)
- **Mission HUD and match overlay** layer over the play HUD (objectives under the Menu button; banner and problem panel above everything); the mission dialogue keeps the old 31 % from the bottom but is lifted clear of the HUD dock when a large HUD size would overlap it. (review: visible)
- **Saves** also keep the control groups (entity ids by slot) besides the world and the camera; a loaded match restores both. Selection and command modes are not kept.
- **The simulation thread** is one merge of both: it presents the seat's view (`Seat`, fog), carries the AI summaries and observer colonies, and takes the screens' controls (pause, save between ticks, chat), notices (network events, the decision) and live status, reports `ready` for networked seats and resumes saves through `Session::local_from`. The mission state for the mission HUD is read from the seat's view.
- **Committed beats play out after `ended`** (`canopy-net`): a slower peer that receives `ended` before simulating the deciding beat keeps getting the beats committed before the end, so every peer reaches the same final state; the end is still reported at once (the result shows from the server's outcome).

## D40. Effects, fog of war, world UI, minimap and portrait (2026-10-15, decided while Jiri was away — review)

[Renderer §9](renderer.md) describes the result; [captures](captures/README.md) (`m3-effects/`) compare every kind of shipped effect with the old game.

- **Authored effects are converted by the cooker** (Q11): `@effects` holds every effect as runtime primitives (particle, decal, mesh, light, sound, plus a ribbon for trails) with the old shape's motion, in seconds, linear colours and pack entry names; `content/effects` stays as authored. Effect image budgets are checked at cook time, model triangle budgets at run time (old `EFFECT_IMAGE_LIMITS`, `EFFECT_MODEL_LIMITS`). Rain and beam layers (unused by shipped data) are converted, warned and not drawn.
- **Cues live on the simulation thread, evaluation on the render thread.** The presenter keeps each cue (one layer for one event) where it stands per tick; the render thread evaluates every cue at the exact render time and the GPU computes each particle from its emitter, index and the old seeded hash. Old timing rules are kept exactly; playback is a function of the time since the cue started, so it is the same at any frame rate and for any shot of the same tick.
- **Budgets** (felt): one global budget instead of the old per-player ones — 256 cues (old: 64), 4 effect lights, 16 effect models with 80,000 triangles, 16,384 particles, 2,048 emitters, 4,096 ribbon quads. In the 8 × 50 crowd battle an aura's ring on every recipient fills the 256 cues. (review)
- **Old-game bugs fixed** (D14): a delivery's projectile effects start once per cast (the old player could restart non-travelling layers bound to `projectile` every frame); a delivery's height is added once to its flight (the old player added the layer height twice to models riding a delivery); standalone plays (shell impacts, construction dust) keep the old rule of ignoring the radius.
- **Effect models are live models with a tint**: alpha below 1 blends over the scene with depth testing and no shadow, as the old transparent effect materials did. The placement ghost uses the same path (translucent at 0.48 like the old ghost instead of screen-door). Uproot's models still look more translucent than in the old game; the cause is not found yet. (review: visible)
- **Fog of war in `scene_out`**: one function every forward pipeline already calls, so terrain, water, scenery, live models, remembered structures and effects darken alike with the old formula; the world UI and HUD do not. The raster (255/90/0, 5×5 box) is kept incrementally by rectangle. Bridge decks fold into the ground cell under them (in sight when any floor is) instead of the old per-floor atlas. The haze is masked as in the old game. (review: visible)
- **World UI**: the game fills a plain `WorldUiInput` (play converts its `WorldUi`); selection rings are draped per sector with the old radial profile computed per pixel (one ring = 48 quads); health and mana bars port the old shader; the mine label uses the bundled Outfit semibold at the old 13/18 px (the old game used the system UI font); rally flags are flat-shaded (the old ones were lit meshes); observers see owned entities with own-colour rings. New, from the brief: thin construction, training and cast bars under the health bar of selected entities (`WorldUiInput::progress_bars`, on). (review: visible)
- **Minimap background is the world seen from above** (renderer §4.4, one source of truth), rendered once when the match starts, instead of the old cartographic palette (terrain paint colours, slope shading, faint scenery). Markers, fog darkening and the view quad follow the old minimap; deposits are told apart by being unowned resources, not by content id. (review: visible)
- **Portrait**: the live model in its own small MSAA pass with the world's tone mapping (D24; the old portrait used ACES at 1.15) and the old key light; no rim light (the lighting model has one sun). (review: visible)
- **WebGPU baseline (D2)**: nothing new is requested (vertex-stage read-only storage buffers and direct draws with a first instance are core WebGPU); no exception needed.

## D42. Render performance: benchmark, levels of detail, graphics presets (2026-10-15, decided while Jiri was away — review)

- **One benchmark** (`just bench-render`, `crates/render/src/bench.rs`, `game/src/bench.rs`): fixed scenes (player base, zoomed-out spectator, the 8 × 50 crowd battle with 256 effect cues, deep water, the deep-forest look, the menu, the HUD) at 1920×1080 and 2560×1600, measured as wall time from recording to idle and every pass alone in its own submit, minus the fixed submit cost; the fastest fifth of 60 frames. Apple's pass timestamps attribute work to neighbouring passes, so they are not used for decisions. The frame log and the debug overlay show a sampled submit-to-idle time instead of summed timestamps (the old "18 ms at 120 fps" reading was that artefact).
- **Levels of detail for live models**, cooked: meshoptimizer simplifies each model (from 1,024 triangles up) into index lists over the same vertices, each level the smallest within a share of the model's size, topology kept (no piece vanishes, seams stay closed). At run time a model draws the coarsest level whose deviation is under `lod_pixels` on screen (High 0.5 px; nobody should see a switch). Shadow casters use the same levels.
- **Cheaper shadows**: one rotation per pixel of a fixed Vogel disk (one sine and cosine instead of one per tap); surfaces facing away from the sun skip the taps; materials skip maps they lack.
- **Graphics presets**, chosen on first run from the adapter's name and changeable in Settings → Graphics (each option can still be set alone): *High* is today's look; *Ultra* finer levels of detail and high haze; *Medium* at most 1440 × 810 scene pixels (upscaled with the sharpen), no contact shading, low haze, LOD 1.5 px, 1024² shadow map; *Low* 1152 × 648, no bloom or haze, LOD 3 px. Apple Pro/Max/Ultra and discrete GPUs get High; **base Apple chips (M1–M4) get Medium**; other integrated GPUs Low. (review: visible — Medium on a base M1 renders below native resolution)
- **Measured** (M4 Max, 40-core GPU): High, worst scene (spectator at 2560×1600) 4.8 ms a frame, the crowd battle 4.1 ms; Medium, worst 2.7 ms (spectator), crowd 2.2 ms, a player view 1.5 ms. CPU recording stays under 0.5 ms, the HUD 0.02 ms. Scaled by GPU throughput (a base M1 has about a seventh), Medium's worst view is about 15–16 ms and a player view about 9–10 ms: 60 fps on a base M1, with the zoomed-out spectator view the tight case. The spectator view is vertex-bound (about 1 million forward and 1 million shadow triangles, mostly scenery and terrain, which Low barely reduces); if the real M1 misses 60 there, the next steps are scenery levels of detail and a shadow distance limit. **Not measured on a base M1** — measure with `just bench-render --preset medium` and adjust `Preset::for_adapter`.

## D43. Desktop updates and releases as before (2026-10-15, Jiri asked for it)

Jiri asked for release 0.3.0 through "the update system same as before", so the updater and release publishing move from phase 2 into phase 1.

- **One release log**, `releases/log.json`, in the old format with its history (0.1.0–0.2.3) and gallery media; every player-visible change gets a note in Unreleased. It is the only changelog: the game's What's new, the feed's notes and the published changelogs come from it.
- **The same host, feed, key and package format**: CloudFront `stable.json` (Tauri's static update JSON), `changelog.json`, versioned immutable files; packages are the `.app.tar.gz` signed with the existing updater key as minisign prehashed Ed25519 whose trusted comment binds the version. Installed copies of the old desktop app therefore update to this game, and this game updates the same way.
- **`canopy-release`** holds the formats and verification shared by the game and the release tool. The app version is the workspace version (`Cargo.toml`); preparing a release sets it.
- **The game's updater behaves as the old one**: it checks on entering the main menu, shows Checking / Latest / Update available / Check unavailable on the version indicator, never downloads or installs on its own, verifies the signature and version before installing, installs only from the menu (never in a match) and restarts.
- **Bundle identifier `com.jiritrecak.settlers`**, the old app's, so an update replaces the old app in place and keeps its identity (release workflow rule). Saves from the old game do not load (D16).
- **The game's updater** (`game/src/update/`, [ui](ui.md#release-plaque-whats-new-and-updates)): a polled state machine on the old `UpdateController`'s phases and messages; the feed is read with a 30 s timeout on its own network thread (reqwest, the multiplayer client's TLS); an update is offered iff the feed's version is newer than the installed one. Packages download into the user cache folder (`Paths::cache`, `updates/`) and are verified with `PUBLIC_KEY` against the feed's version before "Install and restart" is offered. The install (macOS) unpacks the `.app.tar.gz` next to the running bundle (same volume), moves the installed bundle aside, moves the new one in, removes the old one, and moves the old one back if the second move fails; the game then writes its settings, starts the new copy with `open -n` and exits.
- **Installing needs the packaged app**: a development build (not running from an `.app`), a quarantined copy run where it was downloaded (App Translocation) and platforms without packages (Windows, Linux for now) check and show the update with the reason instead of offering the download. An update without a package for this platform is shown as available (the old Tauri check failed instead). (review)
- **The updater lives for the session**: it re-checks whenever the main menu comes up unless an update is already on offer, so a download or a verified package survives a match; a download continues in the background during a match (the old menu-owned controller was discarded when the menu closed). Nothing installs outside the main menu's dialog. (review: felt)
- **The user folder keeps its name** (`com.jt.canopy`) although the bundle identifier changed: the old app's files were its web view's storage, which this game never read, and renaming would orphan this game's settings and saves.
- **What's new is a new design** (Jiri: "nice but also readable", not bound to the old dialog): a timeline of releases beside a reading column — badge, date, the title as a headline, counts by kind, gallery, notes grouped as New, Improved, Fixed and Known issues with their own colours and glyphs, a gallery viewer. It supersedes D38's plaque without What's new. Without an offer the update details show the installed release (the old dialog showed the installed history); an offer without its `changelog.json` shows the feed's plain notes read back by kind. (review: visible)
- **Gallery images ship as files** (`data/releases/media`, from `releases/media/`), read at runtime, falling back to the release host as the old gallery did; checkouts with Git LFS pointers build and show "Image unavailable". The release log itself is built into the executable.
